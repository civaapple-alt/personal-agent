# 运行与协作参考

维护者可在这里查找会话范围、委托与停止语义、成果归档以及经验数据的生命周期。模块和数据流见[架构](../concepts/architecture-and-plan.md)，安装与操作见[文档索引](../README.md)。

## 从用户消息到结果

消息入口与内部委托路径如下：

- 新事项可指定成员，否则使用初始关键词路由，未匹配时交给主要联系人。
- 后续消息默认由事项原负责人处理，并保留已绑定工作区。
- 成员通过 `delegate_to_member({memberId, task})` 决定需要谁的专业工作，`task` 应包含目标、必要事实、约束与期望结果。
- 成员名单来自实际注册的团队，四个初始角色没有写死在委托逻辑中。

执行进程与工具桥接链路如下：

- 执行器每轮启动独立 Pi RPC 进程，但使用持久会话接续。
- Pi 注册的团队工具通过本轮专属的 loopback HTTP bridge 调用编排核。
- 委托者、事项、工作区和调用链由宿主绑定，模型不能在参数里改写身份或跨事项寻址。
- 子成员工具循环完成后，答案作为真实工具结果回到委托者。
- 请求、答案与错误进入 `internal_collab`，工具事件与运行能力清单进入 `notice`。
- 子成员不会向用户频道流式输出，但运行期会将同事进度与 `collabUpdated` 转发给主进度流供工作台即时展示，主联系人负责整合结果。
- 新委托保存 `sourceUserMessageId` 和本轮 `delegationNumber`。执行成员收到任务编号，工具答复向委托方返回同一个编号。转派记录通过 `parentRequestMessageId` 指向上游，回报和失败记录用 `requestMessageId` 关联原任务。SSE 和事项详情快照携带相同的轮次锚点与当前调用关系，网页据此展示交接公告板和实时关系图。
- 旧委托缺少轮次 ID 时，网页根据已有消息的时间和回复范围归入轮次。独立委托和无法确定归属的记录可从历史入口查看。

正式执行的主责可在 `delegate_to_member` 中传入 `verification`，包括 `target`、`criteria` 和可选的 `assignmentNumber`。对象可以是完整 Git 提交哈希、仓库内文本文件，或按标题匹配的本轮暂存文档。引用已有委托时，宿主要求该委托属于当前轮次且已成功回报，验收者与执行者必须是不同成员。

验收使用独立会话，向角色提供目标版本和验收条件，只装配岗位允许的 `read` 和 `bash`。`bash` 仍以宿主权限运行。验收结论有通过、需返工和待复验三种。宿主校验返回结构、文件或文档快照，以及要求仓库证据时的工具完成事件。具体检查结论由验收员提供。对主动送审的文档，归档前比较最终正文的哈希和最新验收结论。

运行巡检根据 Pi 活动和等待状态记录长时间无进展的成员，约三分钟后发出提示并写入 `notice`。已知工具仍在运行、等待用户和内部工具调用时暂停计时。巡检仅报告当前轮次中的活动状态，后续动作由主责或用户决定。

### 等待人类决定

正式执行的主责可使用 `request_clarification` 提交问题、影响说明和可选答案。协作者使用同一工具将待澄清问题连同本轮已有发现返回给直接委托者。主责可以引用当前轮次中直接收到的委托编号，系统据此追溯原始协作者和委托。协作者的 Pi 扩展弹窗同样转成内部澄清，旁听、验收和讨论轮次的弹窗会被取消。主责的短时 Pi 扩展弹窗继续由内存中的 `DialogBroker` 处理。 [Human Question 扩展](../../pi-extensions/human-question/README.md)

主责这轮结束时将问题和选项保存在回复消息中，角色架构师的澄清也用同一记录。依赖该决定的工作按角色指令等待，本轮暂存成果不归档。卡片的状态独立于 Worker 进程。答复写入前核对参与权限、指定答复人、问题版本和当前工作区。提交成功后，用事实和决定接续主责；需要继续内部委托时，主责会收到原委托内容和编号。

角色创建继续走独立的确认接口。旧提案或仍需澄清的提案无法创建角色。应用成功后，提案保留确认人、时间、提案消息 ID、实际角色范围、工具、Skill 和事项加入方式。操作权限继续按目标范围校验。

## 各模块的所有权

| 模块 | 负责的行为 |
| --- | --- |
| `TeamOrchestrator` | 事项负责人、工作区、运行所有权、委托树、用户回复与成果收尾 |
| `execution-context.ts` | Skill 路径解析、保存会话的身份验证、交付文件与 URL 验证 |
| `matter-context.ts` | 基于工作区 ID/路径和明确用户轮次锚点选择复盘/旁听证据及成果 |
| [team-extension](../../pi-extensions/team-extension/index.ts) | 在 Pi 内注册模型工具、装配工具清单、加入当前岗位系统提示 |
| `team-tool-bridge.ts` | bearer token、请求解析、大小限制、调用 ID 去重、连接取消与清理 |
| `PiRpcWorker` | JSONL RPC、确切 session 启动参数、流式事件、settled、模型错误与进程退出 |
| SQLite store | 会话映射、消息、成果版本、原子批量归档与事项执行占用 |

选择独立工具 bridge 是为了保留真实的模型工具调用及返回值：

- 用 `confirm` 对话夹带内部委托会混淆用户确认。
- 直接扩展 Pi stdin RPC 命令则要求修改 Pi 协议或上游。
- 因此 bridge 只承担工具调用传输，执行策略归编排核所有。

## 统一消息路由

工作台先以 `mode: "conversation"` 保存消息。具备 AI 派发权限的用户发言后，系统在同一次事项占用内判断回复、执行、澄清、静默、查询当前成员或查阅功能帮助。关闭主动回应后，AI 仍会处理直接提问和点名，普通团队消息保持静默。成员名单由 PA 从当前配置生成。

- 配置 `TYPESAFE_API_KEY` 时，PA 服务端优先调用 Jev System One。分类请求包含截断后的最新消息、当前工作区的有限前文和必要的候选角色。附件正文和图像不随分类请求传出。
- System One 不可用、超时或返回无效分类时，PA 调用隔离的 `runTypedPiDecision`。两条路径使用同一轮等待预算。模型均不可用时，本地规则可提供名单查询、只读回应或开始执行确认。
- 明确的工作台用法提问可以直接从随版本发布的[功能速查](../guides/agent-workbench.md)回答。实际成员、待答复决定和已发布成果从当前事项读取。点名后的岗位可以通过 `read_pa_help` 按主题查阅。工具读取固定的用户指导和当前工作区已有记录，无需访问业务仓库。
- 明确点名优先决定本轮接收人。已有主责继续作为默认接收人。未确定主责时，PA 在事项允许的成员中匹配角色。角色架构师可在事项中生成待确认提案。
- 执行需由有派发权限的人在最新消息交办。仅靠规则识别出的交办进入确认。附件仅在实际回应或执行时提供。
- 对话回应只装配只读文件工具及岗位已启用的团队咨询工具。正式执行按该角色的工具配置运行。点名对本轮生效，事项负责人继续负责后续。
- 意图不明确时，待决定卡片保存对应的原始消息和答复人。「开始执行」在复核当前权限、角色和工作范围后续跑原请求。「先讨论」启动只读回应。
- 旧客户端仍可通过 `discussion`、`dispatch` 和 `ai_request` 使用显式模式。

## 会话范围与接续

创建事项或调整参与名单只保存配置。正式派发先启动主责。实际委托触发内部会话，主责正常回复后触发旁听会话。同一成员同时参与请教和旁听时，分别使用 `internal` 和 `observer` 会话。每次执行结束后 Pi 进程退出，下次同范围执行会接续保存的会话。

会话查找与启动校验如下：

- 新会话的查找键由事项、成员、组织 ID、工作区 ID、绝对路径和主责、内部、旁听、讨论或验收的会话模式组成（`v2`）。含个人角色上下文的会话再按触发用户隔离。
- 后续轮次把保存的 `sessionFile` 传入 `--session`，不使用 `--continue` 或目录内最近文件。
- 启动前校验 Pi JSONL 首行的 session ID 与真实 `cwd`。
- 保存文件缺失、损坏或属于另一工作区时直接报错，不悄悄创建空会话。

上下文注入与压缩策略如下：

- 系统提示包含岗位定义、工作区范围及执行模式的规则。当前名册、适用经验、目录清单和身份信息变化时，`before_agent_start` 把新快照追加到当前轮次。模型按最新快照判断事项状态。
- 新旧快照相同时，Pi 扩展复用活跃历史中的快照。Pi 压缩移除该快照后，下轮重新附上当前版本。
- 角色规则、真实工具清单或工作区说明变更，以及更换模型或 Pi 压缩历史，都可能影响缓存复用。命中与计费取决于供应商。
- `runtime_model_usage` 执行记录分别提供首个有有效统计的模型请求与该岗位本轮请求的 `input`、`cacheRead`、`cacheWrite`。命中比例为 `cacheRead / (input + cacheRead + cacheWrite)`。记录只覆盖 Pi 回传有效统计的请求。
- **参与阵型与角色架构师隔离**：
  - 当事项处于单兵模式（`solo`，仅 1 位 AI 成员参与且无授权内部协同池）时，宿主从 `--tools` 移除 `delegate_to_member`，系统提示要求按当前名册和已启用工具推进；立项与运行期支持经 `observerMemberIds` 按人切换定向旁听。
  - 内置元角色 `role-architect`（`roleKind: "architect"`）与普通业务名录及自动旁听池隔离，专用于建队对话与团队协作体检。独立规划会话无工具，事项内规划和体检只开放 `read_pa_help`，两者均禁用 Skills 和 MCP。角色架构师生成结构化提案确认卡（含目标 `roleScope` 与可选 `newSkills` 草案）或体检调整建议。经授权用户勾选确认后，PA 才写回对应作用域档案（`.data/roles/` 及 `orgs/<orgId>/`、`users/<userId>/`、对应 `skills/` 目录）与成员记录。运行时 Skill 解析通过 `realpath` 校验落在对应作用域允许目录内，且 `personal` 角色仅供本人查看和执行。

增量交接背景策略如下：

- 首次交接给某成员或在其他成员处理后返回时，宿主最多补充 12 条、20,000 字符的同事项、同组织、同工作区与路径的新增用户频道背景。
- 会话记录中的 `message_cursor` 避免每轮重复加入历史，同成员连续追问直接依赖 Pi 原会话。
- 背景只补充尚未进入当前会话的交流，委托方仍需在任务中给出相关决策和约束。

组织、工作区记忆与 Git 身份隔离如下：

- `company_private` 支持两种绑定模式：
  - 工作区已归属某个 `Organization` 时，该组织下所有工作区按 `orgId` 共享同一组织的经验与记忆，并按组织可选的 `gitEmailDomain` 派生默认 Git 邮箱。
  - 工作区尚未归属任何组织时，继续兼容按单一 `workspaceId` 注入与隔离。
- `project_private` 无论是否同属一个组织，都严格绑定当前工作区 `workspaceId`。
- 无工作区与无组织的旧私有记忆继续保存并可查看，但不会在所有项目执行中加载。
- `role_general` 用于跨组织、跨工作区通用的岗位经验与方法论。
- 每次执行向 Pi Worker 注入对应岗位的 `GIT_AUTHOR_NAME`、`GIT_AUTHOR_EMAIL`，并将当前仓库有效
  `git config user.name/email` 作为 `GIT_COMMITTER_NAME`、`GIT_COMMITTER_EMAIL`（未配置真实用户时回退至岗位身份）。
  - 从而在同一本地仓库内既保留真实用户提交者留痕，又区分不同角色产生的 Git Author 归属，而无需改写 `.git/config`。
- 启动时保证存在默认组织（`org-default` / `默认组织`），通过 API 省略 `orgId` 新建的项目仓库默认归入当前默认组织；
  团队成员池保持全局跨组织协作。

切换组织或工作区后使用另一条 `v2` 会话，切回原范围时恢复其原会话。即使同一个工作区登记后来改了路径，旧会话也不会被移到新目录执行。事项负责人变更会更新事项记录；切回原成员时恢复该成员的会话并补充有界的新交流。

`--no-session` 模式不打开历史 Pi 文件，只用上述有界背景，因此不具备完整的跨进程模型记忆。

## 角色管理一致性

工作台的新建、批量创建、导入和角色调整由同一服务内的写入队列依次处理；架构师对话与团队体检不占用该队列。普通过程交流不因此增加审批步骤。

- 新建显式 ID 与现有成员冲突时返回 409，不再作为覆盖更新。省略 ID 时按岗位头衔生成，并避开已有 ID 和同批次 ID。
- 角色 ID 同时用于文件名，只接受最长 128 字符的小写字母、数字和连接短横线，拒绝 `readme`、路径分隔符和换行。元数据字段及数组条目须单行。职责正文仍支持多行。
- 导入仍可更新同 ID 的业务模板，但不能覆盖内置 `role-architect`；该元角色也不接受权限调整。模板先写临时文件，再原子替换目标文件，不沿目标文件原有符号链接改写其他文件。
- 提案中的新增与调整全部先做输入校验，再写入。重复调整同一成员返回 409。只有 `pending` 提案可以应用；已应用或已忽略的提案不会因重试再次创建成员。
- 删除成功时，在同一 SQLite 事务内记录 `removed_role_templates`。启动同步跳过这些模板，防止内置岗位或残留自定义文件将成员重新创建。显式重新创建或导入会清除标记。删除主联系人、内置架构师、有主责事项或交付成果的成员仍会被拒绝，运行期间仍不可删除。

该队列只协调当前服务的角色管理请求。文件逐个替换，SQLite 与多个角色文件之间没有跨崩溃事务；磁盘故障或进程中断仍需核对实际文件与成员状态。旧版本没有删除标记，不能据此反推出历史删除意图，也不自动清理用户旧文件。

离线回归见 [member-management.test.ts](../../test/member-management.test.ts)，覆盖 HTTP 实际结果、文件内容和数据库重新打开后的状态。2026-11-17，原有 112 项测试通过后，新增回归复现了路径越界、ID 覆盖、提案校验后残留成员和启动复活；修复后全部 119 项测试通过，代码检查、构建、文档检查以及源码/编译入口的文件库/内存库启动检查通过。本轮未重跑真实模型或界面视觉验证，不代表真实模型建队建议的质量已提升。

## 兼容历史数据

数据库兼容初始化与迁移边界如下：

- SQLite 迁移按 `user_version` 执行。升级补齐工作区与经验表的外键并检查现存引用，失败时回滚迁移。已有自定义 Git 署名随库保留。
- 旧记忆缺失的生命周期元数据按原 `verified` 等字段补默认值，不重写消息正文、成果版本或原型。
- 历史成果没有精确应用关联时不从事项历史猜测填充，已有历史评分不自动重算。
- 新会话使用组织感知的 `v2` 范围键。旧 `v1` 和 `context_key IS NULL` 的映射无法证明组织归属，不自动恢复；升级后首次执行建立新会话。旧映射和 Pi 文件继续保存，不删除或改写。
- 新消息在写入时保存有效 `orgId` 快照。没有明确组织锚点的历史消息保留供查看，新会话、旁听或复盘只加载来源范围明确的消息。
- 已有事项、经验、执行历史或授权名单的工作区保留组织归属。若旧数据已出现工作区与事项或消息的组织冲突，工作区私有经验保留在库中，暂时退出执行和网页查询。角色架构师的团队体检只读取通用和授权组织范围的经验。

历史会话与消息的局限如下：

- 旧消息没有可靠工作区标记时保留供用户查看，但不会整体回放到其他执行现场。
- 旧版每轮新建会话造成的历史割裂无法无损还原；组织范围不明的会话只能保留查阅，不能自动接续。
- 旧会话自身保留的历史规则和背景也不会被事后清洗。
- 历史会话丢失时需恢复对应文件，当前尚无自动修复或用户一键重置入口。

## 能力装配与核查

角色 Skill 解析与分享边界如下：

- 角色 `skills` 中的名称解析到仓库 `skills/<name>/SKILL.md`，或解析角色包中的 `skills/<name>/SKILL.md` 相对路径。
- 角色声明对应实际 Pi Skill 文件（含新增的 `technical-writing`），并通过显式 `--skill` 装载；缺失 Skill 会在模型请求前失败。
- 分享角色定义不会把私有记忆打包，也不会自动安装其引用的 Skills 或插件。

扩展与工具清单装配如下：

- 团队执行显式装配扩展与角色 Skills。仅监听回环地址的个人版允许本机所有者的常规岗位执行沿用 Pi 用户配置及受信任仓库的资源。具体范围见[启动与能力装配](configuration.md#cli-启动与能力装配)。
- 主/内部角色 `tools` 加上委托、经验提案工具形成清单；直接负责用户交流的主成员还装配成果发布工具。
- 旁听禁用团队委托、发布和提案；独立 RSI 复盘则不加载工具、扩展和 Skills。
- 内部成员不能直接发布用户成果，宿主也会拒绝伪造的发布请求。
- `mcp` 只是历史声明分类；具体 MCP 需求由 `mcpDependencies` 的服务器名指定，使用现有 Pi 配置。

异步工具校验与能力声明边界如下：

- MCP 或自定义扩展可能异步注册工具。团队扩展最多等待 10 秒，再从 Pi 真实工具注册表筛选所需工具；宿主核查每个普通工具及每个 `mcp__<server>__*` 前缀。
- 缺失能力会明确失败，不能靠提示词声称已具备能力。
- 外部扩展与 MCP 的运行兼容性仍须针对实际配置验证；本轮实机验证没有使用外部 MCP 服务。
- 初始市场角色使用 `read`、`bash`，不再声明未实现的 `web_search`。可用 CLI 或公开页面访问不等于完整搜索服务，研究覆盖范围仍需说明。

## 并发、失败与停止

单事项执行占用与防重入：

- 同一事项同时只有一轮用户执行；进程内运行表与 SQLite 执行占用共同避免两个宿主恢复同一会话。
- 占用记录包含宿主 PID；宿主不存在时，下次显式请求可回收占用。
- 此机制面向单机服务，不是分布式租约，也未防御操作系统 PID 复用。

委托树边界与去重：

- 不同事项可同时执行；一个委托树内，同一成员的同范围会话同时只允许一个执行者，忙碌目标返回工具错误。
- 每轮最多 8 次不同委托，调用链最多 3 名成员，禁止调用自身或祖先。
- 相同委托者、目标和任务在同轮复用结果；相同 transport call ID 和参数只执行一次，ID 对应不同参数时拒绝请求。
- 失败也返回给委托方，由其决定如何继续；不会让用户处理每个内部错误。

取消信号、超时守卫与服务关闭：

- 停止信号传递到主成员、同事及桥接请求；子工具连接关闭只取消该委托子树。
- `abortMatter` 在发出取消、停止 Worker 后等待本轮收尾与执行占用释放再返回，避免停止后立即切换组织仍遇到旧占用。
- 宿主执行桥接工具（如 `delegate_to_member`）阻塞父 Pi 进程期间，父 worker 通过 `suspendIdleTimeout()` 暂停自身 `idleTimeoutMs` 无活动超时。
- 扩展侧使用 `node:http` 且桥接服务侧关闭默认 300s `requestTimeout` / `headersTimeout`，避免长耗时子委托被 HTTP 传输层误掐断。
- 子 worker 由各自的 `idleTimeoutMs`（默认 `15` 分钟，支持 `PA_IDLE_TIMEOUT_MS` 覆盖或设 `0` 关闭）守卫。
  - 整轮可选总上限由 `timeoutMs` 控制（默认 `0` 不设固定墙钟硬上限以支持 Goal/Plan 长任务，支持 `PA_TURN_TIMEOUT_MS` / `PA_PROMPT_TIMEOUT_MS` 设正整数覆写）。
- 单次委托失败后会从本轮成功去重表移除，允许调用方同参数重试；超时属于未完成错误，用户主动停止生成停止回复。
- 启动失败、阻塞对话、模型错误和进程异常均会进入清理路径。
- 服务关闭先停止接收请求、取消对话，再同时取消主执行树和复盘，等待所有 Worker 及复盘结果清理完成后关闭数据库。
- 复盘直到清理结束才移出追踪；取消后的部分 JSON 不提交，新的执行请求也不能在 shutdown 过程中启动。

并发冲突与故障语义：

- HTTP 对同事项重叠消息以及执行中切换工作区返回 409，当前没有运行中 steer 交互；停止、失败或宿主重启后，下一条用户消息明确发起接续，不会自动继续未完成动作。
- 去重范围是本轮内存中的工具调用；硬崩溃后重试模型仍可能再次执行外部动作，没有全局 exactly-once 保证，已写出的文件或对外操作不会因取消自动回滚。

## 人类提请与派发

- 人类协作是共享工作台的写操作分级，不是房间或组织的数据读取隔离。协同成员可讨论、提请与评价，只有所有者能派发或修改运行配置。
- 提请必须为 `channel=user`、`sender_type=user`、`mode=ai_request`、`aiRequestStatus=pending`。存储层以条件 UPDATE 原子认领为 `approved` 或 `dismissed`，并保留处理人和时间；其他消息及已处理提请返回 409。
- 批准先加载附件、校验组织/仓库来源和 AI 成员，再认领并派发。切换范围后的旧提请返回 409，失效附件返回 410，错误成员返回 404，均不提前标为已批准。
- 上传和读取请求体之后，派发入口再次检查事项运行状态。重叠请求返回 409，不覆盖既有进度、不生成伪失败消息。
- 运行中的仓库不能经 PATCH 或同路径 upsert 改归属组织。复盘提交前也重新核对有效组织与仓库；期间发生变化则丢弃结果。
- `approved` 表示所有者已安排执行，并非执行成功；状态转换与外部模型调用不在统一事务内。当前没有崩溃后的自动重派或跨宿主 exactly-once 保证。

## 成果归档

成果发布条件与元数据规则：

- 主成员仅在形成可审阅的阶段成果、用户指定版本或实质变化时，调用 `publish_deliverable` 显式登记成果，提供 `type`、`title`、`changeNote` 与可选 `summary`。正文来源按下述类型规则提供。
- `changeNote` 必须说明本版本的变化及依据，归档在成果摘要中；回复元数据关联成果 ID 与来源用户消息。
- 普通回复、需求澄清、过程进度和细小调整只留在对话，不依赖回复长短、对话轮数或逐次人工批准来判断。

支持以下成果类型：

- `document` 已保存为文件时，传 `sourcePath`，由宿主读取当前工作区内非空 UTF-8 文件，最大 1 MiB，保留完整正文、换行与首尾空白；不再让模型重写另一份正文。没有落盘文件的文档仍可用 `content` 提供完整正文。两者必须二选一，不能同时传；`sourcePath` 不适用于其他成果类型。
- `artifact` 和 `prototype_image` 使用工作区内已存在的实际文件，路径检查解析符号链接并拒绝工作区外文件。
- `service_url` 使用 HTTP 或 HTTPS 链接。语法校验不代表链接可访问、服务仍运行或业务已验收。

旁听评估、事务提交与版本导出规则：

- 内部同事与旁听同事都只从本职专业角度给出判断，不直接发布用户成果（旁听模式下工具装配与宿主桥接同时禁用 `publish_deliverable` 与 `delegate_to_member`）。
- 每轮主成员回复成功后，列席的旁听成员在各自独立的 `observer` 范围会话中并行快速审视本轮对话：
  - 仅接收阶段摘要、已归档成果标题、精简会前摘录及本轮双方最新发言，不读取主成员或其他角色原有 Pi 会话与 `internal_collab` 全量过程日志。
  - 若无实质风险或增量则仅输出 `[SILENT]`（不写入对话流）；确有关键风险或遗漏时，以对应成员头像与「旁听补充」气泡直接发言到主对话流。
- 主成员负责整合并判断是否达到正式交付条件；主成员登记的成果与各执行分支产生的候选经验先暂存，失败分支或主执行取消/失败不提交草稿与候选。
- 文件文档登记时保存路径、解析后的实际路径与 SHA-256 内容快照，来源路径须在工作区内，符号链接也按实际目标校验。主执行成功时再次核查路径和内容；来源已修改、删除或链接改向时拒绝提交旧快照，不悄悄归档变化后的未核查正文。需要修改时先保存，再用新的工具调用重新登记最终文件。
- 同一轮、同一主成员、同标题文档再次登记会替换暂存草稿，本轮只生成一个正式版本；跨轮发布继续新增版本。归档正文是数据库中的历史快照，之后编辑来源文件不改写旧版本。失败或取消不会自动回滚工作区文件。
- 主执行成功时在同一 SQLite 事务中写入成果、候选与版本应用关联；旁听是主回复之后的可选评估，停止旁听不撤销已提交的主结果。
- 相同事项与标题形成版本系列；API 调用方显式提供 `deliverableTitle` 时，仍可导出本轮非空文档回复，默认聊天不导出。
- 工作台已移除根据“修改”前缀强制导出的旧逻辑，“继续修改”只提供对话上下文，不强制生成版本。

事项归档状态边界：

- 本轮成功且有正式成果时才标记 `delivered`，只有聊天、澄清或空正文时保持 `open`。
- 这是归档状态，不代表用户已经验收；文档专业质量、实际文件正确性及服务是否符合需求仍需要具体证据和用户反馈。

## RSI 经验提炼与生命周期

成员经验分为三层作用域，全部本地私有保存，不随可分享模板 `roles/*.md` 导出：

- `role_general`：跨组织、跨工作区通用的岗位经验与工作习惯（`orgId = null`、`workspaceId = null`）。
- `company_private`：若所在工作区已绑定组织则按 `orgId` 跨同组织仓库共享，否则按 `workspaceId` 绑定单个工作区。
- `project_private`：严格绑定当前 `workspaceId`，不跨仓库共享。

执行中的候选与事后复盘采用同一保存边界，但证据来源不同：

- `propose_experience` 将候选写入当前分支的 `ExecutionEffects`（若工作区归属组织，`company_private` 自动归入 `orgId`）。
  - 同事返回有效答案后，effects 才逐层返回主成员；主成员失败时，不会因为同事已经成功就提前落库。
  - 正式成果、候选和精确应用关联在主执行成功后一起事务提交；仅有候选不新增交付物。
- `distillExperiences` 使用 `noSession: true`、`--no-extensions --no-skills --no-mcp --tools ""` 运行。
  - 只处理宿主提供的有界证据（有组织绑定时将 `company_private` 候选落入 `orgId`）。
  - 工作区 ID、路径和明确用户消息锚点共同筛选对话/内部协作/异常；不从事项当前绑定反推所有旧记录的归属。
  - 明确选择版本时只使用截至该版本发布的轨迹与该版本反馈，默认选择最新有同范围来源的成果；无可靠来源的旧成果不能显式作为当前工作区复盘对象。
- 复盘输出最多读取前 8 条候选，非法、越界角色及重复项不落库。
  - 候选归属限于该证据范围内实际参与的角色及显式目标，不会因为数据库中存在某个成员就接受其 ID。
  - 复盘返回后再次核对取消和工作区是否变化，再批量提交候选。

核验、替代链与归属边界：

- 核验通过会将候选改为 `verified`；`supersedesMemoryId` 只允许同成员、同 scope、同组织（`orgId`）、同工作区（`workspaceId`）的无环关系。
- 已经确立的替代链不能清空链接或移动任一端来绕过隔离，旧规则保留为 `superseded` 供追溯；独立、未建立替代关系的记录仍可按用户判断调整归属。
- 提示词区分 `[已验证]` 与 `[待验证]`，但候选当前仍会被注入用于验证，不能把它当作已确认事实或隐私审计。

注入追踪与版本反馈：

- `memory_applications` 中的 `applied` 表示该次执行的当前上下文包含这条经验，`applied_count` 统计适用轮次，不证明模型采纳或能力改善。
- 成功分支的注入 ID 经调用树收集，正式成果发布时写入 `deliverable_memory_applications`；失败分支和发布之后的旁听注入不自动成为该版本的评分对象。
- 成果反馈仅对上述精确关联回写，`memory_feedback_votes` 在每个 `(memory_id, deliverable_id)` 上保存一票当前评价：
  - 相同评价幂等，正负改票撤销上一票再计新票，`neutral` 撤销该版本的贡献；反馈文本、评级、票与计数事务更新。
  - 正负评价过程仍留在应用历史，当前票与历史事件不能当作同一个统计。
- 团队卡片手动 `+1/-1` 为独立人工计数；旧版评分保留，不自动追溯重算，更不能将这些计数描述成因果学习评估。

验收反馈与经验计数在一个事务内保存。若请求附带的自动复盘随后失败，接口仍返回成功保存的反馈及 `distillationError`，界面分别展示两个结果；客户端断连会取消可选复盘。
