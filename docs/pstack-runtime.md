# 在 Pi 的执行内循环使用 pstack

Personal Agent 的外层负责事项、稳定岗位、专业委托、会话接续和成果归档。Pi 的内层负责一轮任务中的模型推理与工具调用。pstack 的 `poteto-mode`、playbook 和原则方法接入这个内层，帮助岗位决定如何调查、设计、实现和验证，不另建一支团队或用户维护的工作流。

本次复用 [backnotprop/pstack](https://github.com/backnotprop/pstack) 的跨宿主镜像。其 `poteto-mode` 已包含 Pi 等宿主的映射和能力缺失处理。没有重写或复制完整 pstack 方法，也不修改本机 Pi 安装。

## 启用完整方法包

### 方式一：启动参数显式指定

```bash
PA_PSTACK_DIR=/path/to/pstack npm run start:web
```

### 方式二：在工作台设置页一键克隆并启用（无启动参数时推荐）

如果启动命令没有设置 `PA_PSTACK_DIR`（例如 `PA_REQUIRE_AUTH=1 PA_HOST=0.0.0.0 PORT=4310 npm run start:web`）：

1. 以**超级管理员**（或未启用强制认证时的本机所有者）进入工作台 **设置 → 扩展插件**（`#/settings/extensions`）。
2. 在 **pstack-extension** 卡片内确认仓库地址（默认 `https://github.com/backnotprop/pstack.git`），点击 **「克隆并启用 pstack」**。
3. 服务端会自动克隆（或复检复用已有目录）到 `<dataDir>/extensions/repo/<仓库名>`（默认仓库为 `.data/extensions/repo/pstack`），校验 `plugin.json` 与 `skills/poteto-mode/SKILL.md` 完整性后立即生效，并将该路径持久化保存在 `platform_settings.pstackDir` 中；后续不传 `PA_PSTACK_DIR` 重启服务仍会自动加载。可在同一卡片内按需「同步更新」或「停用」（如通过启动环境变量 `PA_PSTACK_DIR` 启动，则环境变量优先接管）。

`PA_PSTACK_DIR` 指向同时包含 `plugin.json` 和 `skills/poteto-mode/SKILL.md` 的完整包根目录。无论通过启动参数还是页面克隆目录，运行时均以只读方式读取其 Markdown 正文，不自动修改包内容；程序化调用仍可向 `TeamOrchestrator` 传入 `pstackDir`。

当前 Codex 会话提供的 pstack 插件是 ChatGPT 精简适配版，含部分方法和原则，其 README 明确说明不包含全部自主编程流程。该安装目录没有 `poteto-mode`，不能直接当作本次完整方法包来源。外层助手拥有某个插件，也不意味着 Personal Agent 的 Pi 子进程自动继承它。

未配置时沿用原有岗位方法。显式配置的包缺少模式、清单或方法文件时，执行报错，不静默回落成已启用。清单版本和模式正文 SHA256 留在 `runtime_ready` 通知里；版本来自外部包声明，哈希只标识实际读取的正文，不代表完整依赖锁定。

## 方法正文在需要时进入上下文

执行器仍使用 `--no-extensions --no-skills` 隔离隐式发现，再显式提供岗位 Skills、pstack 的模式入口及本项目方法读取扩展。方法工具必须通过实际工具清单握手，否则在业务提示执行前报错。

新增的 `load_pstack_skill` 用法：

| 调用参数 | 返回内容 |
| --- | --- |
| `{}` | 当前包实际可用的方法名称和描述 |
| `{ "name": "poteto-mode" }` | 模式完整原文 |
| `{ "name": "poteto-mode", "resource": "playbooks/bug-fix.md" }` | 对应 playbook 原文 |
| `{ "name": "principle-fix-root-causes" }` | 原则的完整 `SKILL.md` |

每次成功读取返回原文、实际路径和 SHA256。模式与原则的 `disable-model-invocation` 元数据不会被误当成已经装载正文；本项目提供显式读取路径。实质任务先读取模式，再按任务选择方法。简单问候、确认以及没有实质风险的旁听不要求先装入完整模式。

本项目目前为 `poteto-mode` 的 `playbooks/bug-fix.md` 补充显式装载依赖：读取这个调试流程时，一并读取 `principle-fix-root-causes` 和 `principle-prove-it-works` 的原文，逐份返回路径及哈希。它解决实机中“选了流程却跳过原则”的问题，没有修改外部方法包；其他流程仍按需读取，不宣称已有完整依赖解析器。正文进入上下文不等于模型正确应用。

读取工具只接受包内有目录记录的方法和 Markdown 资源，拒绝越出 `skills/` 的路径与符号链接、非 Markdown 和超过 256 KiB 的文件，不执行附带脚本。它与岗位的通用文件工具分开，因此纯文稿岗位、无业务工具的角色架构师和旁听成员也可以读取方法，不因此获得读取业务文件或修改代码的权限。Pi 本身仍不是操作系统沙箱。

## 内循环服从实际岗位与宿主边界

- 主责、内部成员和旁听都可以使用方法；它们实际拥有的文件、命令和团队工具仍由原来的执行装配限制。
- pstack 提到专业协作时，使用当前事项允许的 `delegate_to_member`。它是已有岗位的咨询，不是任意子代理、外部 agent CLI 或工作树启动器。单兵模式仍没有委托工具。
- 主责才可发布正式阶段成果。内部成员不能发布，旁听不能委托或提出经验候选。方法包中的通用发布流程不改变这些宿主规则。
- 角色架构师启用后只有方法读取工具，仍没有业务文件、终端、委托、发布或经验工具。既有无 pstack 的零工具模式保持原行为。
- 包中的模型选择、会话扫描、自动化或分享建议不授予额外操作权限；模型与会话由本项目选择，普通交流不新增用户审批。

这一轮只接入正常岗位执行。独立的阵型 JSON 决策、快速角色设计模型和经验反思仍保持既有无工具隔离，不自动增加 pstack 上下文。没有实现完整第三方插件市场、依赖安装、任意子代理运行器或所有宿主工具的自动转换。

## 用真实任务检查装载和行为

```bash
npm run demo:pstack -- --source /path/to/pstack
```

`--help` 不调用模型；正常运行调用本机 Pi 与真实模型，会消耗 Token。脚本复制方法包的 Skills 到临时目录，创建独立数据库、会话和合成项目，不使用 `.data/` 或已登记业务工作区。

两个场景分别检查：

1. 产品经理在没有通用文件和终端工具时实际读取 `poteto-mode`，讨论尚未决定的到期行为，不提前产生正式交付。
2. 研发经理处理倒计时函数的可复现缺陷。宿主先证明固定测试失败，角色再执行修复，宿主重跑同一份未被修改的测试。同时检查模式、根因与验证原则的成功读取记录，方法副本保持不变，普通过程没有正式成果。

证据目录保留 `report.json`、`proof.db`、Pi 会话、合成项目和方法副本。通过表示指定装载链路与确定性任务结果满足检查，不表示各岗位的语义质量、长期可靠性或方法带来的因果收益已得到证明。需要评估质量改善时仍须固定同题输入，重复运行并独立审阅。

离线回归见 [pstack-runtime.test.ts](../test/pstack-runtime.test.ts)：真实资源读取、流程依赖正文、错误路径指引、路径与大小边界、目录查询、取消、架构师/旁听工具范围、静默以及缺失工具握手。它不调用真实模型。[证据判定](../src/demo/pstack-evidence.ts)要求成功完成的方法工具结果同时含目标原文与对应哈希，仅提及名称、只有哈希、失败或未完成均不通过。

## 实机结果记录

2026-11-17 首轮证据目录为 `personal-agent-pstack-zB2VkP`。产品经理实际读取模式，但随后有一次原则路径调用失败；研发经理实际读取模式与修复 playbook，修复后固定测试通过，但未读取原则正文却在回复中引用原则，演示因此判定失败。该记录保留，不改为通过。

第二轮 `personal-agent-pstack-gBhUIT` 补充了正确调用示例、当前 Worker 成功读取清单及读取与应用的区别。模型没有再引用未读原则，固定测试也通过，但仍未装载原则正文，因此依旧失败。仅改指引未解决装载缺口。

第三轮 `personal-agent-pstack-tHxH7U` 在同一调试流程中显式装载两份原则依赖，两场景通过。再用同一套“完整原文＋哈希”判定器离线复核三轮：前两轮缺少原则正文，第三轮返回了实际正文与哈希。模式和方法副本保持不变，测试文件未被改写，没有正式交付。

三轮使用相同两项用户任务，共六轮主负责人真实执行。倒计时修复在三轮均通过固定测试，因此这次改善的是方法材料装载，不是已经证明修复质量提升，也不是模型自主选择原则已经稳定。产品对话只检查模式装载、工具范围和不提前归档，未作独立语义审阅。测试经理、市场负责人及旁听的真实任务表现仍未在本演示中验证。

本批 139 项离线测试、代码检查、构建、四种启动检查及文档检查通过；另直接调用构建后的方法扩展，确认能返回 playbook 与两份原则的原文、路径和哈希。构建检查与离线检查不新增模型请求。

上述早期任务中含有“按 pstack 方法工作”的提示，因此不能据此认定用户完全不点名时仍会主动选择方法。针对这一限制另补[五类自然任务验证](pstack-selection.md)，保留当前运行指引作为基线，并将目标方法观察和回答质量分别审阅。
