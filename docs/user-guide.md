# 使用指南

在工作台交办事项、验收成果和管理团队。首次安装见[安装与首次运行](getting-started.md)，主要概念见[设计思路](design-principles.md)。

## 交办一件事

在新建事项中说明目标、已有资料、期望成果和约束。涉及文件时，选定组织和仓库；首次启动自动登记的 `personal-agent` 是本项目自身，不是你的业务仓库。

如果你在本机所有者模式下为已有仓库交办任务，Pi 会沿用你已启用的用户 Skills 和扩展，以及它信任的仓库 `.agents/skills` 和 `.pi/` 配置。带项目资源的仓库如尚无可信决定，可在该仓库的 Pi 中确认信任。 [本机资源配置](configuration.md#cli-启动与能力装配)

团队版普通账号需要先创建或加入组织。选定仓库时，事项沿用该仓库的组织。未绑定仓库时可以选组织，留空则使用自己所属的默认组织，或所加入的第一个组织。发起 Role Architect 对话时同样可以选择组织，仓库选择会隐藏。

一个可用于设计阶段的描述：

> 为小团队设计一个反馈收集盒。先读取已有资料，明确首版用户、范围和验收条件；产品经理牵头，必要时请教研发和测试。目前不编码、不提交 Git。形成可审阅方案后再发布 V1，过程讨论不归档。

发送前，在输入区顶部核对发送方式、组织和仓库。用输入区左下角的 `+` 附加资料。

- 图片支持 PNG、JPEG、WebP 和 GIF，每次最多 6 张。也可以拖拽图片或按 `Ctrl/Cmd+V` 粘贴。
- UTF-8 文本与代码文件每次最多 6 个，单文件上限 512 KB。
- 直接粘贴达到 600 字符或 10 行的纯文本时，工作台将其折叠成附件。发送前可预览或选择「放回输入框」继续编辑。发送后从消息中打开附件。

信息不足时，可以先发起讨论，请负责人补齐关键问题。

## 选择讨论与 AI 执行方式

| 方式 | 适用情况 | 实际行为 |
| --- | --- | --- |
| 团队聊天讨论 | 交换信息、查证和讨论方案 | 默认只保存人类消息。开启「AI 参与讨论」后由 AI 参与，可用 `@` 点名在组角色 |
| 给 AI 安排事项 | 快速确认分工并正式推进 | 由主负责人执行，可按需委托并发布阶段成果 |

在「调整参与方式」选择一人处理或团队协作。旁听把关可以独立开启，每个非主责角色也可分别勾选「按需请教」和「旁听把关」。按需请教发生在主责工作期间，旁听在主责回复后核对风险，必要时补充。

AI 讨论沿用岗位工具配置，可以用命令查证仓库状态。讨论模式是对 AI 的工作指引，工具仍使用宿主机权限。讨论回复留在聊天中，正式执行与交付使用「给 AI 安排事项」。已有 AI 轮次正在运行或额度耗尽时，讨论消息仍会保存。

输入区的主责、请教与旁听名单决定实际安排。即时规则评估不调用模型。主动请求 AI 判断会调用 Pi，可选择允许只读查仓，并查看实际读取依据。静默旁听也可能调用模型，时序见[旁听演示](observer-demo.md)。

## 延续、停止与修订事项

在原事项继续提问，系统按保存的成员、组织和工作区上下文接续确切 Pi 会话。修改负责人或工作区会改变上下文范围，不等于把所有旧模型历史搬到新范围。

运行中需要取消时使用**停止**。同一事项执行期间不能再派发一轮，也不能切换负责人或工作区；可调整参与、旁听名单及旁听开关。刷新页面用于查看当前状态，不等于取消任务。

失败后先保留错误和过程记录，处理原因再继续。丢失或损坏的 Pi 会话会明确报错，当前没有用户一键修复入口，也不会静默创建空会话冒充接续。停止或失败不保证撤销已经发生的文件或外部工具操作。

## 审阅成果并反馈

在**交付成果库**打开阶段成果，核对本版重点、正文、文件或服务链接，以及需要时展开的过程依据。普通问答和澄清不会因为回复长而自动成为交付物。

对修订任务明确指出原版本、发现的问题及预期改变，例如：

> V1 中处理状态只有待处理和已完成。V2 增加处理中，并说明与合并、重开、迁移及验收条件的关系。保留 V1，保存新文件；研发和测试有不同意见时先澄清，再发布最终方案。

在对应版本记录验收评级和意见，再在事项中继续提出修订要求。反馈保存、后续 AI 执行和经验提炼是不同操作；若界面提示“验收已保存、复盘未完成”，先确认已保存意见，不要把可选复盘失败当成验收丢失。

正式文件通过 `sourcePath` 发布时，宿主读取并核对登记时的快照。这能防止归档正文与发布时文件分叉，不能证明跨章节规则或验收条件正确，也不保证文件以后被外部修改后仍与归档同步。

服务链接是交付的一种形式。查看链接的实际可访问状态，本地预览由宿主管理，重启后不会自动恢复预览进程；成果记录存在不代表服务持续在线。它不是持久部署。

## 调整岗位模型

四个业务岗位模板默认使用 `kimi-coding / kimi-for-coding`。换模型时，先确认 Pi 已配置对应访问权限，再为每个实际参与的业务岗位执行：

1. 在**我的团队**导出该成员能力包，保存一份原始副本。
2. 在 Markdown frontmatter 修改 `defaultProvider`、`defaultModel` 和模型支持的 `thinkingLevel`，保留原 `id` 与职责内容。
3. 导入修改后的能力包。同 ID 的普通业务角色会更新，运行期模板保存于 `.data/roles/`，不会回写仓库基线 `roles/`。
4. 检查成员配置与依赖，再进行一次范围明确的试用。

内置 `role-architect` 是受保护的系统角色，不能用同 ID 包覆盖；普通角色的模型修改不要被理解为全局模型切换。当前没有覆盖全部系统决策与元角色的统一模型配置入口。字段与依赖格式见[配置参考](configuration.md)。

导出包不包含数据库中的私有记忆，但不能自动识别写在角色正文中的秘密。分享前检查正文、工具依赖和路径。角色导入也不会附带别人已积累的工作经验。

## 核验经验与扩充能力

在团队或成果的经验面板查看候选经验，核对来源、适用组织或仓库，再选择核验、编辑、忽略或替代。注入次数和评价计数只是追踪线索，不能证明经验提高了结果质量。

用角色架构师规划岗位，或手动导入定义。使用前核对职责、Anti-Jobs、Skills、工具和验证方式。

| 角色范围 | 谁能创建和使用 | 存储位置 |
| --- | --- | --- |
| 平台通用（`global`） | 超级管理员创建，跨组织使用 | `.data/roles/`。根目录里的旧自定义角色沿用此范围 |
| 组织共享（`org`） | 组织管理员或超级管理员创建，成员在所属组织内使用 | `.data/roles/orgs/<orgId>/` |
| 个人私有（`personal`） | 活跃的普通成员也可按配额创建。只有创建者可以查看、使用和管理 | `.data/roles/users/<userId>/` |

快速创建角色或通过角色架构师设计岗位时，可以同时生成 Skill 草案。勾选要采用的草案，再编辑 ID、正文和位置。确认创建或应用提案后，工作台才将所选 Skill 保存到角色包的 `skills/<name>/SKILL.md` 或所选的全局、组织、个人 Skill 库。

完整 pstack 包是可选项。管理员可在「设置 → 扩展插件」克隆并启用它，也可在启动时用 `PA_PSTACK_DIR` 指向已有的包。操作步骤见[pstack 运行说明](pstack-runtime.md)。

## 保存与备份运行资料

默认情况下，数据库、Pi 会话、上传与自建角色都在项目 `.data/` 中，业务成果还可能保存在所关联的外部工作区。备份前停止服务及相关执行，保留完整目录和真实工作区，避免只复制一个正在写入的 SQLite 主文件。

如果设置了 `PA_DB_PATH`，数据库同级的 `roles/` 与 `inner-matter/` 随数据库目录移动。会话和附件仍保存在启动目录的 `.data/pi-sessions` 和 `.data/uploads`。恢复时一起保留这些目录和原工作区路径。完整路径见[配置参考](configuration.md)。

升级前备份，使用同一数据目录时让新版本做现有增量迁移。不要通过删除 `.data/` 处理兼容问题；数据库迁移不等于承诺可以直接降级到旧二进制。若从个人本机免密试用直接切换到团队共享部署，兼容细节与安全清单见[从个人本机试用切换到团队共享部署](getting-started.md#从个人本机试用切换到团队共享部署)。

## 团队账号、超级管理员与组织协作

共享服务请开启 `PA_REQUIRE_AUTH=1`，通过 HTTPS 反向代理访问。部署步骤见[团队启动](getting-started.md#方式-b多人团队共享服务推荐开启权限控制)。

1. **设置平台权限。** 初始化首个超级管理员后，打开侧栏的「超管控制台」。在「平台安全边界」设置注册策略、克隆主目录、本地仓库路径白名单和命令型预览权限。在「组织与运行任务」可以中止异常任务。操作记录见「安全审计日志」。
   - `open_review` 默认开放注册。超管在「用户审核与配额」通过审核后，账号才可使用。
   - `open_auto` 开放注册并自动启用账号。
   - `invite_only` 只允许持有效组织邀请码的人注册。
2. **创建并配置组织。** 账号启用后，可在「我的团队 → 新建组织」按配额创建组织、勾选所需 AI 角色。之后在组织卡片的「AI 角色」调整名册、主联系人和角色 Git 署名。默认沿用仓库自己的 Git 用户配置。若要采用角色署名，开启该组织的「AI 角色独立 Git Author 署名」。个人私有角色使用单独的 `maxPersonalRoles` 配额。
3. **邀请同事。** 组织所有者或管理员在组织卡片打开「人类成员 → 组织邀请码」，选择成员角色并生成链接。未登录的同事打开链接后进入注册页，审核通过即可进入邀请组织。已登录的浏览器会先要求确认使用当前账号，或选择「退出并注册新成员」。
4. **登记仓库并设置事项范围。** 在「项目仓库与资料 → 登记项目仓库」可从 Git 地址克隆到 `<workspacesRoot>/<orgSlug>/`。将仓库设为组织内可见，或通过「受限」名单授权。已有事项、经验、执行历史或授权名单的工作区保留原组织归属。新建事项时，在「调整参与方式」选择组织可见或私密。私密事项对发起人、所选人类成员和有权管理该组织的账号开放。普通组织成员可在权限和并发配额内派发 AI 任务，只读访客可查看已授权内容。
5. **查看和管理成果。** 成果库按组织身份、仓库权限及事项范围过滤结果。可组合组织、项目和可见范围筛选成果及其预览。事项创建者、组织所有者或管理员以及超级管理员可修改成果访问范围。组织所有者与管理员可管理本组织经验，只读访客可查阅授权成果。

## 与同事在局域网协作

未开启用户账号体系的小规模同网协作仍支持局域网邀请口令：从工作台 **我的团队** 管理内网协同同事并生成邀请链接，再显式扩大绑定范围：

```bash
PA_HOST=0.0.0.0 PORT=4310 npm run start:web
```

将终端列出的可达局域网地址与邀请链接分享给同事；若需公网或正式团队长期共享访问，请开启 `PA_REQUIRE_AUTH=1` 并通过 HTTPS 反向代理部署，安全边界见[安全说明](../SECURITY.md)。
