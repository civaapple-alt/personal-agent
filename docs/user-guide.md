# 使用指南

本文面向已启动工作台的使用者。首次安装见[安装与首次运行](getting-started.md)；概念之间的关系见[设计思路](design-principles.md)。

## 交办一件事

在新建事项中说明目标、已有资料、期望成果和约束。涉及文件时，选定组织和仓库；首次启动自动登记的 `personal-agent` 是本项目自身，不是你的业务仓库。

一个可用于设计阶段的描述：

> 为小团队设计一个反馈收集盒。先读取已有资料，明确首版用户、范围和验收条件；产品经理牵头，必要时请教研发和测试。目前不编码、不提交 Git。形成可审阅方案后再发布 V1，过程讨论不归档。

先核对输入区顶部的发送方式、组织与仓库选择（所有会话页均统一收敛在同一输入卡片顶部），再点击发送。需要附带上下文时，可点击左下角 `+` 上传图片（PNG/JPEG/WebP/GIF，最多 6 张，也支持拖拽或 `Ctrl/Cmd+V` 粘贴）或 UTF-8 文本/代码文件（最多 6 个、单文件 ≤ 512KB）；直接粘贴 ≥ 600 字符或 ≥ 10 行的大段纯文本会自动折叠为胶囊，发送前可点击预览或「放回输入框」继续编辑，发送后仍可在消息气泡中点击查看。没有提供足够信息时，让负责人提出必要问题即可，不必先替所有岗位拆完任务。

## 选择讨论与 AI 执行方式

| 方式 | 适用情况 | 实际行为 |
| --- | --- | --- |
| 先讨论 | 同事先交换信息，还未决定派发 | 只保存团队讨论，不启动 AI |
| 一人处理 | 一位岗位即可完成 | 限定主负责人，不委托、不旁听 |
| 按需请教 | 主负责人需要其他专业判断 | 从允许参与的成员中按需委托，不是全员同时执行 |
| 加人旁听 | 需要指定岗位检查风险 | 主负责人回复后，旁听成员检查并按需补充或静默 |

侧边推荐只是建议，实际发送配置以输入区的主责、参与和旁听名单为准。即时本地规则评估不调用模型；主动请求 AI 判断会调用 Pi，可选择允许只读查仓。允许读仓不等于读取成功，查看评估中的实际读取依据。推荐也不会自动安装缺少的岗位或依赖。

内部咨询对话可以按需展开。旁听不保证每次发言，静默评估仍可能产生模型调用。它也不是与主负责人同时工作的常驻线程，具体时序见[旁听演示](observer-demo.md)。

## 延续、停止与修订事项

在原事项继续提问，系统按保存的成员、组织和工作区上下文接续确切 Pi 会话。修改负责人或工作区会改变上下文范围，不等于把所有旧模型历史搬到新范围。

运行中需要取消时使用**停止**。同一事项执行期间不能再派发一轮，也不能切换负责人或工作区；可调整参与、旁听名单及旁听开关。刷新页面用于查看当前状态，不等于取消任务。

失败后先保留错误和过程记录，处理原因再继续。丢失或损坏的 Pi 会话会明确报错，当前没有用户一键修复入口，也不会静默创建空会话冒充接续。停止或失败不保证撤销已经发生的文件或外部工具操作。

## 审阅成果并反馈

在**交付成果库**打开阶段成果，核对本版重点、正文、文件或服务链接，以及需要时展开的过程依据。普通问答和澄清不会因为回复长而自动成为交付物。

对修订任务明确指出原版本、发现的问题及预期改变，例如：

> V1 中处理状态只有待处理和已完成。V2 增加处理中，并说明与合并、重开、迁移及验收条件的关系。保留 V1，保存新文件；研发和测试有不同意见时先澄清，再发布最终方案。

在对应版本记录验收评级和意见，再在事项中继续提出修订要求。反馈保存、后续 AI 执行和经验提炼是不同操作；若界面提示“验收已保存、复盘未完成”，先确认已保存意见，不要把可选复盘失败当成验收丢失。

正式文件通过 `sourcePath` 发布时，宿主读取并核对登记时的快照。这能防止归档正文与发布时文件分叉，不能证明跨章节规则或验收条件正确，也不保证文件以后被外部修改后仍与归档同步。

服务链接是交付的一种形式。查看链接的实际可访问状态，本地预览由宿主管理，重启后不会自动恢复预览进程；成果记录存在不代表服务持续在线。它不是持久部署。

## 调整岗位模型

四个业务岗位模板默认使用 `kimi-coding / kimi-for-coding`。换模型时，先确认 Pi 已配置对应访问权限，再为每个实际参与的业务岗位执行：

1. 在**我的团队**导出该成员能力包，保存一份原始副本。
2. 在 Markdown frontmatter 修改 `defaultProvider`、`defaultModel` 和模型支持的 `thinkingLevel`，保留原 `id` 与职责内容。
3. 导入修改后的能力包。同 ID 的普通业务角色会更新，运行期模板保存于 `.data/roles/`，不会回写仓库基线 `roles/`。
4. 检查成员配置与依赖，再进行一次范围明确的试用。

内置 `role-architect` 是受保护的系统角色，不能用同 ID 包覆盖；普通角色的模型修改不要被理解为全局模型切换。当前没有覆盖全部系统决策与元角色的统一模型配置入口。字段与依赖格式见[配置参考](configuration.md)。

导出包不包含数据库中的私有记忆，但不能自动识别写在角色正文中的秘密。分享前检查正文、工具依赖和路径。角色导入也不会附带别人已积累的工作经验。

## 核验经验与扩充能力

在团队或成果的经验面板查看候选经验，核对来源、适用组织或仓库，再选择核验、编辑、忽略或替代。注入次数和评价计数只是追踪线索，不能证明经验提高了结果质量。

新增岗位可用角色架构师规划或手动导入定义；真正使用前核对职责、Anti-Jobs、Skills、工具和验证方式。完整 pstack 包是可选项，按[pstack 配置说明](pstack-runtime.md)显式设置。宿主助手安装过插件，不会自动让本项目 Pi 成员拥有它。

## 保存与备份运行资料

默认情况下，数据库、Pi 会话、上传与自建角色都在项目 `.data/` 中，业务成果还可能保存在所关联的外部工作区。备份前停止服务及相关执行，保留完整目录和真实工作区，避免只复制一个正在写入的 SQLite 主文件。

`PA_DB_PATH` **只重定向部分路径**：数据库同级的 `roles/` 与 `inner-matter/` 跟随迁移，但会话仍在启动目录的 `.data/pi-sessions`，上传仍在 `.data/uploads`。保留原工作区和会话路径关系；仅恢复数据库无法重建全部上下文。精确位置见[配置参考](configuration.md)。

升级前备份，使用同一数据目录时让新版本做现有增量迁移。不要通过删除 `.data/` 处理兼容问题；数据库迁移不等于承诺可以直接降级到旧二进制。

## 团队账号、超级管理员与组织协作

当团队部署共享服务器（建议开启 `PA_REQUIRE_AUTH=1` 与反向代理 HTTPS）时，系统提供多成员邮箱注册、超级管理员台账与分组织权限边界：

1. **初始化与注册**：首次启用 `PA_REQUIRE_AUTH=1` 打开网页即引导创建首个**超级管理员（`super_admin`）**；管理员可在左侧栏底部的 **超管控制台（`#/admin`）** 设置注册模式（开放自动启用 / 开放需超管审核 / 仅组织邀请）、默认配额、多团队代码库克隆主目录（`workspacesRoot`）与本地目录白名单，并随时审核、启用/禁用账号、调整组织数量上限及并发 AI 执行额度，或查看安全审计日志与紧急中止运行中任务。
2. **自建组织、人类成员与 AI 角色**：任何已启用的成员可在配额内点击 **我的团队 → 新建组织** 创建自己的组织，通过邮箱直接添加同事或签发带角色（`org_admin` / `org_member` / `org_viewer`）的一次性/限次组织邀请链接（`?invite=orginv_...`），并在组织内单独勾选启用的 AI 角色及组织主联系人。
3. **项目隔离与事项范围**：
   - 登记项目仓库时优先选择「从 Git 地址克隆到组织主目录」，仓库将隔离保存在对应组织目录下；项目和事项均支持按 `org`（组织内全员可见）或 `restricted` / `private`（仅授权成员可见）控制访问范围。
   - 普通组织成员（`org_member`）可在已授权的组织、项目与事项范围内直接「给 AI 安排事项」触发执行；只读访客（`org_viewer`）与被管理员关闭派发配额的账号不能直接触发 AI。

## 与同事在局域网协作

未开启用户账号体系的小规模同网协作仍支持局域网邀请口令：从工作台 **我的团队** 管理内网协同同事并生成邀请链接，再显式扩大绑定范围：

```bash
PA_HOST=0.0.0.0 PORT=4310 npm run start:web
```

将终端列出的可达局域网地址与邀请链接分享给同事；若需公网或正式团队长期共享访问，请开启 `PA_REQUIRE_AUTH=1` 并通过 HTTPS 反向代理部署，安全边界见[安全说明](../SECURITY.md)。
