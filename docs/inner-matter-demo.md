# 内置演示事项

演示使用虚构的“小团队反馈收集盒”，体验需求讨论、专业协作、阶段交付和反馈修订。它使用正常事项、真实岗位工具、会话与成果版本；没有预制 AI 对话或交付结果。

## 打开与体验

1. 启动或重启工作台：在仓库根运行 `npm run start:web`。
2. 以所有者身份进入“新建事项”，点击“体验内置演示”。首次打开会准备 Git 工作区、登记独立演示组织和事项；不会调用模型。
3. 按引导点击“填入提问”，可修改文字后再发送给产品经理。后续执行使用本机已有 Pi 模型配置。

| 步骤 | 操作与可观察结果 |
| --- | --- |
| 需求讨论 | 产品经理读取背景和虚构访谈，概括问题并提出最多三个关键问题；不归档成果 |
| 专业协作 | 填入范围确认，产品经理实际委托研发经理和测试经理，再整合建议；仍不归档 |
| 阶段交付 | 明确要求形成 V1，保存方案文件并发布 document“反馈收集盒 · 产品方案” |
| 反馈修订 | 给 V1 记录试用意见，再发送修订要求；保留 V1 并发布同一标题的 V2，可在成果库比较版本 |

第四步会保留已有的 V1 验收意见；没有文字意见时才记录示例反馈，不改变已有验收评级，也不自动触发经验复盘。要求填入输入框后仍需发送。可以在成果库修改验收意见，再继续讨论。

引导中的“已有记录”从持久消息、成功内部回复、正式版本和反馈计算。点击按钮本身不算完成；如果模型未真实委托或发布，后续步骤不会被标记为已有记录，可以在对话中要求团队补齐。

## 工作区与保留规则

默认工作区为仓库根的 `.data/inner-matter`：

- `README.md`、`AGENTS.md`：背景入口与演示约定。
- `docs/brief.md`、`docs/customer-notes.md`：初始产品资料，明确标记虚构来源。
- `deliverables/`：初始为空，实际执行后生成 `feedback-box-v1.md`、`feedback-box-v2.md`。
- `.git/`：首次创建的独立 Git 仓库，不自动提交，不改写其他仓库配置。

设置 `PA_DB_PATH` 后，演示目录跟随数据库所在目录，使用其同级的 `inner-matter/`；`:memory:` 启动不提供该入口。测试使用临时路径。演示目录不是操作系统沙箱，角色仍以本机用户权限运行。

重复打开会复用同一事项，只补齐缺失的初始文件，不覆盖用户修改、重置 Git 或删除版本。演示使用独立组织“内置演示团队”，不替换当前默认组织。需要已存在的产品经理、研发经理和测试经理；缺少角色会明确报错。若手动改变了演示事项的组织或仓库，系统不会自动把它改回来。

## 代码与验证入口

- [演示定义](../src/demo/inner-matter-definition.ts) 保存四步提示与共享类型。
- [准备服务](../src/server/inner-matter.ts) 维护文件、独立组织和固定演示事项 ID；`POST /api/demos/inner-matter` 只允许所有者调用。
- [网页引导](../web/src/components/chat/InnerDemoGuide.tsx) 展示步骤，[进度计算](../web/src/innerDemo.ts) 读取实际记录，不另存一份演示进度。
- [离线回归](../test/inner-matter.test.ts) 使用受控 Worker、真实工具桥接和临时 HTTP/SQLite，验证前两轮无交付、V1/反馈/V2、重复打开与权限边界。
- `npm run demo:inner` 显式调用真实 Pi，在系统临时目录跑完四步，保留 `proof.db`、会话、方案文件和 `turns.json`。它不操作 `.data/inner-matter` 或用户运行数据库。

选择按需打开而非启动时自动灌入事项，是为了保留已有工作台与用户选择；选择复用正常执行链路而非录播，是为了让演示暴露实际协作和交付行为。演示仅覆盖一项小型设计任务，不代表多日自主工作或岗位能力已经充分验证。

2026-11-16 验证结果：90 项离线测试、类型/规范检查、构建、源码与编译入口启动及文档检查通过；Chrome 已查看桌面和 375px 窄屏的打开、填入与刷新。真实 Pi 也完成四轮：前两轮零成果，随后 V1、反馈、V2，主负责人始终使用同一会话，结束没有残留事项占用。实机证据见[运行说明](runtime-collaboration.md#2026-11-16-内置演示四步实机验证)。
