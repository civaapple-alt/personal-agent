# 0.10.x 规模拐点架构演进方案（8 万 → 15 万行工程底座升级）

> **文档状态**：演进蓝图与分阶段落地记录（对应 [未来版本提案 P-0908](future-proposals.md)）。其中**阶段 0（样式层收敛：Tailwind v4 + 纯 React Primitives）**、**阶段 A（P1 · 前端状态与数据层解耦：`A-1` Zustand 分域 Store + `A-2` TanStack Query 收口查询型页面）**与**阶段 B（P1/P2 · 后端 HTTP 路由与边界校验：`hono` 声明式路由 + `@pa/contracts/schemas` Valibot 运行时契约）**已完成编码、边界门禁与单测/E2E 验证；其余阶段（`C` / `D`）尚未开始，待按需分批推进，不改变当前产品主线范围，也不得表述为已上线能力。

随着 Personal Agent 能力面不断扩展，代码仓库已从早期的轻量工具跃迁至中等复杂系统。本文在保持 **三环硬边界多包架构** 与 **Pi 原生单轨内核** 的前提下，系统性规划项目从 **8 万行生产代码向 10–15 万行演进** 时的底座升级路径，避免「早期零依赖手写最优解」在更大规模与高频 AI 协作下演变为结构性维护税。

### 1.2 为什么需要分阶段换底座（AI 协作下的「复制税」）

```text
0–3 万行（探索期）      ──▶ 零依赖原生手写最轻快，文件少，人脑可直接装下全局约定
3–8 万行（成长后期）    ──▶ 局部复制开始划算于跨模块抽象；若无统一原语，AI 会安全地“再写一套”
8–15 万行（平台期）     ──▶ 跨层状态同步、接口校验与 Schema 演进成为主成本，必须用高共识薄原语锁死边界
```

- **先行验证的样板（阶段 0 · 已完成）**：Web 端早期手写全局 CSS 曾膨胀到 **22 个文件、11,185 行**（515 处 `display: flex` 及大量仅差几像素的重复卡片/胶囊），核心诱因就是人或 AI 改动旧样式风险高，宁可新建局部前缀。切换到 **Tailwind v4 + 纯 React Primitives**（[ui-design-system.md](../reference/ui-design-system.md)）并配合 `@tailwindcss/node` / raw hex 门禁后，样式直接收口为 **6 个文件、830 行（降幅 92.6%）**。
- **下一个逼近拐点的三层**：把同一规律投射到逻辑层，当前仓库里已经能看到明确拐点顺序：**前端状态透传** > **后端路由与边界校验** > **SQLite 类型安全查询** > **前端开发热更新体验**。

## 2. 阶段 A（P1）：前端状态与数据层解耦

### 2.1 当前问题与示例

1. **状态过载与透传深**：[App.tsx](../../apps/web/src/App.tsx) 作为根壳同时管理会话、侧栏筛选、草稿、弹窗、SSE 进度与各面板刷新（26 个 `useState`），并通过 [AppStageRouter.tsx](../../apps/web/src/views/AppStageRouter.tsx) 向 [ChatStage.tsx](../../apps/web/src/views/ChatStage.tsx) 透传 95 条 props。新增跨页面动作往往要连续修改 4–5 个组件签名。
2. **数据请求与缓存散落**：`bootstrap`、事项详情、工作区、空间文档、看板状态由多个 hooks 各自维护 `loading`/`error`/本地状态，SSE 事件回流时容易出现局部状态分叉或整树重渲染。

### 2.2 落地与演进方案（`3 + 1` 分层：URL + TanStack Query + Zustand UI/实时态）

- **阶段 A-1 · UI 与实时域 Zustand Stores（已落地）**（置于 [apps/web/src/stores/index.ts](../../apps/web/src/stores/index.ts)，单向依赖约束由 [check-module-boundaries.mjs](../../scripts/check-module-boundaries.mjs) 强制校验，`stores/` 禁止反向依赖组件/视图/hooks/queries，`api/`、`utils/`、`primitives/` 禁止依赖 `stores/`）：
  - `useWorkbenchStore`（[workbenchStore.ts](../../apps/web/src/stores/workbenchStore.ts)）：当前路由与子页签、侧栏搜索/折叠、全局通知横幅、删除/归档确认弹窗开关及本地偏好持久化（[storage.ts](../../apps/web/src/utils/storage.ts)）；
  - `useSessionStore`（[sessionStore.ts](../../apps/web/src/stores/sessionStore.ts)）：bootstrap、认证态、组织列表、当前选中组织/工作区与视图加载开关；
  - `useMatterRuntimeStore`（[matterRuntimeStore.ts](../../apps/web/src/stores/matterRuntimeStore.ts)）：事项列表/详情、`progressByMatter`、`progressStartedAt`、`streamingDelta` 与活跃 run 快照；
  - 保留 `ElapsedTimer` 叶子组件独立每秒计时的性能边界，并通过细粒度 selector 隔离订阅范围（`streamingDelta` 仅由 `AppStageRouter` / `ChatStage` 消费，不回灌 `App.tsx` 或 `Sidebar.tsx`）。
- **阶段 A-2 · 查询型页面收口 TanStack Query（已落地）**（置于 [apps/web/src/queries/index.ts](../../apps/web/src/queries/index.ts)，由 [queryClient.ts](../../apps/web/src/queries/queryClient.ts) 与分层 [queryKeys.ts](../../apps/web/src/queries/queryKeys.ts) 统一管理，`queries/` 同受单向依赖门禁保护）：
  - 覆盖外围与面板类请求-响应接口：管理台与运行底座（[useWorkbenchPanels.ts](../../apps/web/src/hooks/useWorkbenchPanels.ts)）、资料空间列表/文档/Git 提交详情（[SpacePages.tsx](../../apps/web/src/views/SpacePages.tsx)）、工作区目录规则与关联文档（[WorkspaceDetailPanel.tsx](../../apps/web/src/components/WorkspaceDetailPanel.tsx)）、团队成员 Skill 详情预览（[MemberInspectorModal.tsx](../../apps/web/src/components/team/MemberInspectorModal.tsx)）、组织邀请列表（[OrganizationDetailPanel.tsx](../../apps/web/src/components/OrganizationDetailPanel.tsx)）；
  - 同步拆除 [SpacePages.tsx](../../apps/web/src/views/SpacePages.tsx) 内重复创建的第二条 `EventSource`，改为由全局单一 SSE 通道 [useMatterEventSync](../../apps/web/src/hooks/useMatterEventSync.ts) 统一按事件域调用 `workbenchQueryClient.invalidateQueries`（覆盖 `space_updated` / `space_page_updated` / `matter_settled` / `workspace_updated` / `team_updated` / `organization_updated` 与断线重连兜底失效）；登出/吊销会话时由 `clearPanels()` 清空 Query 缓存，避免跨账号残留。

#### 2.2.1 前端 `3 + 1` 状态分层决策与选型依据

针对 Agent 实时工作台特性，PA 前端收敛为如下四层明确归属，避免把“请求缓存”写回 Zustand、也避免把“逐 token 推流”硬塞进 Query：

| 状态层级 | 负责工具 | PA 覆盖范围 | 选型与边界说明 |
| --- | --- | --- | --- |
| **1. URL 与导航状态** | 现有 [hashRouter.ts](../../apps/web/src/hashRouter.ts) | 顶层视图路由、`matterId`、`pageId`、子页签等深链 | PA 是 CLI 托管静态 Hash SPA，路由层级浅、无 SSR/嵌套 loader 需求；维持零构建 codegen 轻量 Hash 路由，**暂不引入 TanStack Router** |
| **2. 服务端请求-响应缓存** | `@tanstack/react-query`（[queries/](../../apps/web/src/queries/index.ts)） | `spaces`、`workspaces`、`team`、`organizations`、`admin`、`settings` 等查询型页面 | 统一承担 loading/error、竞态取消、跨面板共享缓存与 mutation/SSE 后按域 `invalidateQueries`，禁止再手写 `useState + useEffect + cancelled` 样板 |
| **3. 纯前端全局 UI 状态** | **Zustand**（[workbenchStore.ts](../../apps/web/src/stores/workbenchStore.ts)） | 侧栏折叠/搜索、全局横幅队列、确认弹窗、本地偏好 | 相比 RTK 无 Action/Slice 样板税，相比 React Context 无全子树重渲染问题，相比 Jotai 更适合跨域工作台布局状态 |
| **+1. Agent 高频 SSE 实时运行态** | **Zustand**（[matterRuntimeStore.ts](../../apps/web/src/stores/matterRuntimeStore.ts)） | `streamingDelta`（逐 token 增量）、`progressByMatter`、`progressStartedAt`、`activeRuns` | Agent 流式推送频率远高于普通 CRUD 轮询，不宜交由 TanStack Query 管理；通过 Zustand selector 隔离到 `AppStageRouter` / `ChatStage` 叶子层消费 |

### 2.3 迁移与验收策略

1. **阶段 A-1 落地结果**：已完成 `useWorkbenchStore`、`useSessionStore`、`useMatterRuntimeStore` 三域剥离，`App.tsx` 从 `821` 行 / `26` 个 `useState` / `95` 处 JSX prop 绑定收敛为 `698` 行 / `0` `useState` / `51` 处 JSX prop 绑定，`SidebarProps` 由 `23` 项收口为 `11` 项，`WorkbenchBanners` 归零 props；[web-stores.test.ts](../../test/web-stores.test.ts) 通过。
2. **阶段 A-2 落地结果**：已落地 [apps/web/src/queries/](../../apps/web/src/queries/index.ts)、SSE 单通道域失效、`spaces` / `workspaces` / `team` / `organizations` / `admin` / `settings` 六类查询视图与面板迁移、拆除 `SpacePages` 重复 `EventSource`，并补齐 [web-queries.test.ts](../../test/web-queries.test.ts) 与 `queries/` 单向边界门禁；`npm run check`、`npm run build`、`npm test`、`npm run check:startup`、`npm run check:docs` 与 `npm run e2e` 全通过。
3. **后续按需精细化（暂不强制）**：若 `bootstrap` / 事项详情本身也出现多套局部缓存协调诉求，再评估是否进一步从 Store 下沉到 Query；Board 局部面板高频 SSE 仍维持现有增量通道。

## 3. 阶段 B（P1/P2 · 已完成）：后端 HTTP 路由与运行时边界校验

### 3.1 问题回顾与设计取舍

1. **手写路由分发线性增长**：原 [packages/server/src/server/routes/](../../packages/server/src/server/routes/context.ts) 下 15 个路由模块依赖 `handlers` 顺序轮询与手工 `req.method === ...` / `pathname.startsWith(...)` / `decodeURIComponent` 切片，路径参数增多后易产生匹配顺序耦合。
2. **编译期契约与运行时校验割裂**：`@pa/contracts` 统一了 TypeScript DTO，但入口缺少跨端复用的轻量运行时 Schema 与统一 HTTP 错误映射通道。

### 3.2 实际落地架构（`hono` + `valibot` `@pa/contracts/schemas`）

- **零膨胀路由层（`hono` + Node 适配器）**：
  - 在 [router.ts](../../packages/server/src/server/router.ts) 实现 `createApiRouter`、`dispatchHonoRequest`、`requireAuthMiddleware`、`requireSuperAdminMiddleware` 与 `parseJsonBody`，统一映射 `HttpRequestError`（含 `CodedError`）响应、多值 `Set-Cookie`、`BASE_SECURITY_HEADERS` 与 `x-pa-route-miss` 回退；
  - 在 [http.ts](../../packages/server/src/server/http.ts) 新增 `HttpRequestError` 并将 `readRawBody` 收敛为按 `IncomingMessage` `WeakMap` 记忆化的 36 MiB 限流读取；
  - 将全部 15 个业务/管理/认证路由模块迁移为声明式 `register*Routes(app)`，在 [app.ts](../../packages/server/src/server/app.ts) 按 `/api/*` 挂载 `publicApiRouter` 与 `apiRouter` 并移除旧 `handlers` 轮询分发器（`/api/events` SSE 与 `/api/uploads/:filename` 流式读取继续由 `app.ts` 在进入路由前直接处理）。
- **运行时契约单一事实源（`valibot` -> `@pa/contracts/schemas`）**：
  - 在 [packages/contracts/src/schemas/index.ts](../../packages/contracts/src/schemas/index.ts) 新增子路径导出 `@pa/contracts/schemas`（`common`、`board`、`matter`、`space`、`organization`、`admin`、`skill-trust`），使用无宿主依赖的 `valibot` 描述 Schema 与 `InferSchemaOutput`。
  - **兼容性边界**：为保持既有中文/英文 400 错误文案与现有集成测试及前端行为一致，部分路由优先通过 `parseJsonBody(c, Schema)`（如 `DialogRespondSchema`、`JoinOrgSchema`、`UpdateWorkspaceFolderSchema`、`UpdateWorkspacePiTrustSchema`）做直接校验，其余路由通过 `parseJsonBody(c)` 解析对象后沿用领域级校验，后续新接口默认优先复用 `@pa/contracts/schemas`。

### 3.3 验收结果

- 新增 [test/server-router-schemas.test.ts](../../test/server-router-schemas.test.ts) 覆盖 `@pa/contracts/schemas` 运行时校验、Hono 路由鉴权/超管中间件、错误映射、多 `Set-Cookie` 透传与 `app.ts` 零遗留 `handle*Routes` 断言；
- 保持单向三环依赖边界与单文件 `< 1000` 行零豁免通过 `npm run check`、`npm run build`、`npm test`（`288/288`）、`npm run check:startup`、`npm run check:docs` 与 `npm run e2e`（`3/3`）。

## 4. 阶段 C（P2 · 按需触发）：SQLite 类型安全查询与迁移层

### 4.1 触发阈值（不要提前过度工程化）

当前 [packages/server/src/storage/](../../packages/server/src/storage/)（23 张表、6,841 行）运行稳定且已由 [database-schema.md](../reference/database-schema.md) 与迁移测试覆盖。仅当以下条件之一出现时触发本阶段：

- 数据表数量突破 **35–40 张**（如审计流水、多组织配额、扩展持久化表持续增加）；
- 字段重构频繁导致手写 SQL 拼装与 `row as ...` 类型强转出现漏改风险；
- 需要多维度组合筛选查询而手写动态 `WHERE` 拼接变得难以审计。

### 4.2 目标方案（薄层类型安全 Builder + 显式版本迁移）

- 引入 **Kysely** 或 **Drizzle Core**（底层仍走本机已有 SQLite 驱动，**禁止改变嵌入式零运维数据库定位**），让表列名与关联查询直接在 `tsc --noEmit` 阶段报错。
- 保留 `user_version` 整数版本演进纪律与 `0x50413730` 等历史库无损升级路径，新增迁移继续由单元测试校验幂等性与索引完备性。

## 5. 阶段 D（P2 · 按需触发）：前端开发期 Vite HMR

- **现状**：[build-web.mjs](../../scripts/build-web.mjs) 使用 70 余行 `esbuild` + `@tailwindcss/cli` 直接产生产物 `apps/web/dist/`，冷构建极快、零开发服务器维护成本。
- **演进方向**：只有当 UI 密集开发频繁需要保留 React 组件状态实时热更新（HMR）时，再为开发态评估接入 **Vite Dev Server**（代理 `/api` 与 `/api/events` SSE 到 Node 宿主）；**生产分发仍必须产出静态资源包直接由 `apps/cli` 宿主托管**，不改变单命令启动与桌面发布形态。

## 6. 跨阶段设计铁律与非目标

1. **门禁永远先于重构**：任何基础设施迁移前，必须保留并同步升级仓库自动化门禁（`check:boundaries` 三环隔离、`check:sizes` 单文件 `<1,000` 行零豁免、`check:css` 语义校验与 `e2e` 真实浏览器测试），防止新旧体系混战回弹。
2. **顺着 Pi 纹理生长**：所有工程层重构只解决软件宿主规模复杂度，**禁止自造平行 Agent 运行时**；Pi 子进程、`--session`、`SKILL.md` 与 `tool_call` 门禁继续保持单轨原生机制。
3. **只换薄标准件，不做全盘停工大重写**：遵循「基座试点 → 实机/测试验证 → 分批清退旧层 → 锁死门禁」节奏（与样式迁移相同），每一步均可随时合入 `main` 并交付可用版本。
4. **明确非目标**：
   - 不引入 NestJS / Next.js 等重型全栈框架（会破坏三环边界与本地轻量 CLI 交付定位）；
   - 不为追求技术时髦提前切换分布式数据库或消息队列。
