# 设计思路

Personal Agent 希望减少用户同时充当产品、研发、测试与市场岗位的负担。稳定的岗位负责持续理解事情和推进工作，使用者聚焦目标、必要决策和成果验收。

本文解释设计取舍；模块和数据流见[架构说明](architecture-and-plan.md)，讨论脉络保留在[讨论记录](../history/product-discussion.md)（早期 V1–V4 图像演进已归档至本地 `.notes/prototypes/`）。

## 岗位稳定，工作可以跨项目

产品经理对需求与范围负责，研发经理对技术方案与实现负责。参与哪个仓库由当前事项决定，岗位职责不因切换项目而重新定义。

这让用户可以先提出事情，再找相关角色，而不必每次从一个空的项目 Session 开始组织所有专业判断。具体文件操作仍需要明确工作区，跨项目不表示不同公司或仓库的私有信息可以混用。

## 用事项连接工作，用成果承接变化

群聊能表达交流，却容易把重要决定淹没在消息中；复杂任务看板又把维护流程的成本交给用户。当前选择以事项保存连续交流及参与范围，以正式成果承接可审阅的阶段变化。

事项仍可以持续，不要求一轮对话结束就产生一个版本。一次专业咨询可以只留下过程，形成明确方案或实质修订后再发布。周报、月报可从工作记录回顾，不作为用户必须维护的主流程。

| 概念 | 在本项目中的职责 |
| --- | --- |
| 角色定义 | 可分享的职责、方法、工具依赖与不做清单 |
| 成员 | 执行该岗位的本地实例、模型配置与私有经验关联 |
| 事项 | 一件持续推进的工作、参与成员及上下文范围 |
| 组织与工作区 | 公司背景、仓库位置与范围过滤的依据 |
| Pi 会话 | 对应成员在确切事项范围内的模型执行历史 |
| 成果版本 | 显式发布的阶段快照、变化说明及版本反馈 |
| 经验 | 有来源、范围与核验状态的可复用判断或方法 |

这些概念各有职责。数据库中的成果版本与可继续修改的文件是两份状态；成员私有经验也不是可分享模板的一部分。

## 主负责人整合专业判断

用户面对一位主负责人。主负责人按需通过真实工具咨询允许参与的成员，并整合结果；内部成员返回专业意见，不能自行发布最终成果。单人模式则由执行器关闭委托能力。

旁听承担补充审视。当前是在主回复后检查风险，必要时发言，没有新意见时静默。增加旁听人数会增加潜在模型开销，咨询发生也不表示意见正确或被有效采纳。

默认界面保留关键沟通和可查看的交付。需要补充背景、决定方向或授予操作权限时再找用户，不把每次内部讨论都做成审批节点。

## Bot、Skill 与 Plugin 分别承担什么

Bot 或岗位定义回答“谁负责什么”；Skill 描述“一类工作怎样做”；Plugin 可以打包方法、扩展及工具集成。成员的实际能力由定义、已装载资源、可用工具和执行环境共同决定。

Personal Agent 外层管理事项范围、真实委托、会话及成果；Pi 内层运行模型推理与工具循环。可选 pstack 包提供模式、playbook 和原则，进入这个内循环，不替代成员身份与事项编排。

本地 `technical-writing` 是已归属标注的适配方法。完整 pstack 由操作者另行提供，没有自动插件安装、跨宿主完整适配或版本依赖解析。配置方式见[启用 pstack](../guides/pstack-runtime.md)，方法装载结果见[验证记录](../validation/pstack-checks.md)。

## 能力约束由运行结构落实

角色正文中的“不能发布”只是一条指引。当前由工具装配和宿主校验共同限制内部发布、越界来源、单人委托以及会话范围，不能用增加提示词代替这些执行约束。

同样，应用层只读或工具白名单不构成操作系统沙箱。尤其带 `bash` 的角色仍可能访问本机其他资源；组织背景过滤也不等于成熟多租户访问隔离。信任与暴露边界见[安全说明](../../SECURITY.md)。

## 持续成长需要结果证据

目标是让成员在工作、反馈、整理经验、再次应用和修正中进步。当前实现候选提案、只读复盘、人工核验、替代和版本关联，尚未实现可持续后台自主成长，也没有因计数增加就认定能力提高。

评估需要用相同问题的修订前后结果比较事实依据、跨章节规则和验收条件。方法读取记录证明材料到达，真实委托记录证明咨询发生，版本数量证明发布发生；这些都不能单独证明质量改善。已有失败结果保留在[发布复核](../validation/publication-review.md)和[自然方法选择验证](../validation/pstack-selection.md)。

## 当前取舍与后续方向

当前优先验证能否可靠接续工作、找对专业角色、形成有依据的成果并保留修订历史。损坏会话的明确恢复入口、成果与文件或服务状态的一致性、预览重启策略及真实外部工具配置验证仍需完善。

下一步由具体问题、可观察结果和回归证据驱动。长期后台自治、完整 RSI 和公开人才市场保持为目标，不以配置文件或角色数量宣布完成。最新排期与实现边界以[架构计划](architecture-and-plan.md)为准。
