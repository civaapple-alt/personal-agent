# Personal Agent 产品方向确认稿

状态：产品方向的确认依据与长期目标。面向新读者的当前介绍见[项目首页](../README.md)，设计取舍见[设计思路](design-principles.md)，最新机制与验证范围见[运行说明](runtime-collaboration.md)。本文保留早期未定问题，长期目标不代表已全部实现。

## 产品定位

Personal Agent 是一支长期为使用者工作的 AI 团队。成员按岗位组织，身份和职责相对稳定，能够跨多个产品、项目和仓库履职。

用户希望减少自己同时覆盖所有岗位思考和工作的负担。各角色应当从本职视角补充判断、承担工作，并在实际使用中逐渐提升能力。

此前关于公司产品立项、研发、发布和迭代的讨论提供工作背景。产品范围目前围绕个人使用的角色团队展开。

## 初始角色示例与可组合团队

此前暂按以下四个角色组织初始团队。用户进一步提出人才市场与按需组建团队的方向，成员可以根据产品和工作需要选用、复制和调整。这四个岗位作为当前起点。

| 角色 | 职责重点 |
| --- | --- |
| 市场与营销负责人 | 真实用户需求、目标客户、细分市场、竞品、价值表达、推广与试用反馈 |
| 产品经理 | 用户问题、需求范围、优先级、验收条件，以及将相关依据转化为产品选择 |
| 研发经理 | 实现方案、任务拆分、依赖、交付进展与阻碍 |
| 测试经理 | 验证范围、验收用例、质量风险、缺陷与测试结论 |

市场研究与营销暂由同一角色承担。当前研发经理可在授权范围内编码，测试经理可执行验证；并非每个事项都需要进入实现阶段。实际工具与岗位方法见[角色设计](role-design.md)。

## 人才市场与角色能力定义

用户希望借鉴 Grok Bot 的人才市场，将认为有价值的 Bot 角色展示、分享出来，供别人选用或复制。

角色的整体能力由职责、技能，以及依赖的工具、插件等组合形成。使用者可以查看这些定义，选择预设角色，或复制他人的角色后按需要调整，再组建适合自己产品和工作的团队。

这个方向与跨项目履职结合：成员仍按岗位工作，团队成员的选择和组合可以因实际需要而变化。不同团队、产品与成员之间的具体对应关系尚未确定。

助手建议区分可分享的角色定义与实际加入团队的成员。成员逐步学习到的公司、项目背景和工作经验如何与定义关联，哪些内容可以继续分享，仍需设计。

结合用户提供的具体市场案例，助手进一步提出一份待核对的角色定义结构：职责与边界、技能和工作方法、工具与环境依赖、协作和沟通约定、交付与验证方式。

角色创建辅助、跨成员协调及专业研究曾作为能力组合候选，目前内置角色架构师作为元角色，其余岗位保持按需设计，公开人才市场仍未实现。参考起点为 [Grok Bot Marketplace](https://x.ai/bot/marketplace)。

## 日常工作与协作

- 用户有统一的参与入口，可以提出问题、讨论和交办事情，发起工作不以先进入某个项目会话为前提。
- 角色有自己的任务列表，工作可以关联不同产品或项目。
- 角色在职责范围内稳定推进自己的事情，必要时自行联系其他角色开展协作。
- 需要用户补充信息或做判断时，再向用户提出。用户日常主要看到成果和必要沟通。
- 角色间的协作对话自然留存，用户需要时可以查看。过细的内部过程不作为默认展示重点。

当前采用统一工作台，以事项承接连续交流、以成果库展示版本。早期的微信群、同事群类比不等于将集中群或一事一群作为产品的基本组织方式，具体使用见[使用指南](user-guide.md)。

## 分散信息与自然积累

实际工作涉及公司与行业背景、产品文档、会议讨论、客户反馈、仓库和研发记录。信息可能交叉影响多个产品、事情和角色，需要承接这种复杂性。

仓库自身维护的信息，以仓库为准。

用户希望工作过程自然留下可用记录，方便随时了解当前情况和回顾近期进展，减少自己重新翻消息、分类和整理的负担。周、月回顾的需求仍存在，其基础应当来自平时的工作积累。

信息怎样关联、哪些变化形成工作记录，以及怎样保持认识与当前事实一致，仍需设计。

## 角色持续成长

角色像入职后的员工一样，逐步熟悉公司、行业定位、产品和工作背景，并提高履职能力。

持续成长是团队共同原则。工作、反馈、经验整理、后续应用与修正构成目前讨论的成长方向。用户曾以 RSI 描述这一期待，具体学习机制和效果衡量尚未确定。

## 成果与交付体验

成果和交付物需要清楚记录、展示。用户从布置工作的视角，可以直接查看或体验交付，判断是否达到自己的预期，并继续给出反馈。

过程回复、需求澄清和细小的讨论调整默认只保留对话。形成可审阅的阶段成果、明确版本或实质变化时，才正式发布并记录变化依据，关联具体成果及其版本。由成员判断并推进，用户不需要每次手动批准归档。

交付形式可以包括文档、文件、原型，以及独立运行的简单服务或前后端应用链接。用户能够点开链接查看和体验，不要求全部成果都嵌入 Personal Agent 内部。

当前已实现显式成果登记、版本与反馈关联，以及独立服务预览链接；具体的归拢与演示体验仍可继续改进。原型探索继续按版本保存，旧图、用户反馈和新版变化共同保留。

## 已反馈不合适的方向

- 以 Jira 式项目研发生命周期管理为主要产品形态，让用户维护繁重的任务与流程。
- 把零散工作简单归入一个大群或为每件事新建群，让用户继续自行整理消息。
- 把定期填写、整理周报月报作为掌握工作情况的主要方式。
- 默认展示大量内部过程和依据，增加用户盯进度、审细节的负担。

## 早期开放问题与当前进展

以下是早期讨论留下的设计问题。事项、明确主责、显式成果、范围记忆与依赖装配已有基础实现，体验完善和长期能力验证仍在继续，不能将整张清单理解为尚未开始，也不能当作全部完成。

- 统一入口、角色交流和成果记录如何共同组织，是否需要固定的主要联系人。
- 角色如何接收和安排任务，如何使用资料、访问项目并持续开展工作。
- 不同角色、公司与项目背景之间，经验和信息如何区分与共享。
- 成果如何持续归拢、关联反馈，以及服务链接如何运行和访问。
- 持续学习如何实现，怎样判断角色真的提高了工作能力。
- 人才市场的角色定义如何分享、复制和调整，如何关联依赖；角色定义、实际成员与成长经验如何区分。

## 当前工作阶段

产品已从早期文字确认进入可运行工作台与真实任务验证阶段。0.6.0 的文档组织、许可及公开前状态见[开源准备说明](releases/v0.6.0.md)。

当前已有基于 Pi RPC 的可运行工作台，支持可组合角色定义、按事项和工作区接续会话、模型工具发起的内部委托，以及正式成果的显式归档与版本记录。实现方式、兼容规则和限制见[连续上下文与内部角色协作](runtime-collaboration.md)。

本轮最小真实 Pi 验证覆盖了产品经理咨询研发经理、连续过程交流不新增交付、宿主重启后接续同一会话，以及随后明确发布一个 V1。这是有限场景的运行证据，不代表完整岗位能力、多日自主工作或长期成长已验证。

持久后台任务、完整 RSI 流水线、公开人才市场及自动依赖安装仍未完成。角色定义导入导出与基础依赖装配已实现，不等于完整市场能力。此前网页试用所绑定的业务项目仅提供背景，本轮未对其开展业务实现。
