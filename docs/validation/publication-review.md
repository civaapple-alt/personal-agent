# 验证阶段发布前的负责人复核

本项验证分别检查发布链路、按场景要求协作的行为，以及最终正文质量。它是开发验证工具，不在日常产品中增加会签或逐次人工审批。

## 运行对照

命令在仓库根运行。执行场景会使用本机 Pi 发出真实模型请求并消耗 token，不属于离线测试；查看帮助和离线汇总不调用模型。

```bash
npm run demo:review
npm run demo:review -- --scenario required
npm run demo:review -- --scenario solo
npm run demo:review -- --scenario all
npm run demo:review -- --scenario autonomous --repeat 3
npm run demo:review -- --help
```

默认只运行 `autonomous` 的一组基线/当前方法配对。`--repeat` 支持 1–10，每次使用全新的数据库、工作区和会话；同一场景相邻重复轮次交换两种方法的先后顺序。`all --repeat 3` 会执行三个场景的三次配对，即 18 轮主任务，额外同事调用按场景和模型决策发生。控制台在执行前打印主任务数量。

| 场景 | 要回答的问题 | 专业协作要求 |
| --- | --- | --- |
| `autonomous` | 面对矛盾设计稿，负责人会怎样自行判断、修订与协作？ | 记录行为，不因未咨询直接判失败；质量另行审阅 |
| `required` | 已明确要求研发与测试核查时，是否真实委托、整合并发布？ | 两位岗位均须在最终成功登记之前返回，否则本场景协作失败 |
| `solo` | 只修正通知人数与称谓，能否保持范围并正确交付？ | 产品经理可自行完成，按需咨询即可 |

脚本创建系统临时目录。每个场景的两组使用相同的合成 V1/V2、任务、岗位定义与模型配置，thinking 均设为 `off`。基线组只移除新增的负责人复核方法，仍可以自主咨询；当前组保留该方法，也没有宿主强制会签。这是方法对照，不是重放旧提交的全部运行环境。脚本不读取或修改用户运行数据库及已登记业务仓库。

V1/V2 是明确标注的合成输入，不属于本次模型产出。复杂场景没有逐条告诉模型矛盾位置；只有 `required` 显式要求两位岗位参与。复杂场景的正文审阅标准为：

| 问题 | 审阅标准 |
| --- | --- |
| 虚构需求被写成已试用、已验收 | 修正结论，准确区分设计、假设和实际验证 |
| 子条目冻结与验收要求同步写子条目冲突 | 正文、状态规则与验收条件采用一致语义 |
| 新增字段却宣称无需结构变更 | 明确结构迁移与状态数据迁移的区别 |
| 重开保留完成时间，迁移却用全库计数断言 | 迁移限定版本或旧记录范围，重复执行不会误判合法重开条目 |

## 查看证据

控制台输出证据目录。先读 `case.json`，核对每个场景的输入、协作要求、配置哈希与审阅问题，再比较三层结果：

- 每轮目录为 `<场景>/repeat-<次数>/<baseline或current>/`，`workspace/` 保存模型处理的合成资料。
- `evidence.json` 保存原始检查、实际工具时序与内部咨询；`proof.db`、`sessions/` 保留执行记录。
- `published.md` 是宿主从数据库正式版本导出的最终正文快照。质量审阅针对这份快照，不采用模型回复里的“已通过”自评。
- `quality-review.json` 初始逐项为 `pending`。独立审阅者填写姓名、各项 `pass` 或 `fail`、解释及引用；`evidence` 每条须有从 1 开始的 `line` 与该行完整原文 `text`。保留原有正文哈希，不重写最终稿来配合评分。
- `newIssues` 保存修订中发现的新增问题，同样提供解释和行号引用；`severity=blocker` 会使质量判为失败，即使已有标准均通过。
- `summary.json` 与 `summary.md` 分开报告 `publication`、`collaboration`、`quality`。统计保留每组全部轮数，未审阅、无效和缺失记录分别计数；`pairs` 仅在双方标准均完成审阅后列出已修正、退步和仍失败的标准，以及新增阻塞问题数。

`publication` 检查执行成功、V1/V2 保留、单个 V3、实际文件来源、精确正文匹配与占用清理。`collaboration` 按场景报告 `pass`、`fail` 或 `not_required`，同时保留实际咨询岗位和缺少的岗位。`not_required` 不代表质量通过。

完成独立审阅后运行离线汇总，仅刷新汇总文件，保留正文、执行证据和审阅输入：

```bash
npm run demo:review -- --summarize <证据目录>
```

汇总会验证审阅对应最终正文哈希、每项标准恰好出现一次、结论有解释且引用行与原文完全匹配。旧正文的审阅、缺项、无效引用和改动过的发布快照均不能得到质量通过。这些校验确认记录来源和完整性，不自动证明审阅者的语义判断正确。

退出码 `0` 表示各组各层均通过，且质量已有有效的独立审阅记录；`1` 表示至少一组存在发布失败、未满足本场景明确协作要求、质量失败或无效审阅；`2` 表示尚未观察到上述失败，但质量仍未完成审阅。新执行结束通常先显示 `INCOMPLETE` 并返回 `2`。基线失败属于对照结果，不代表当前方法一定退步，差异须查看逐组结果和 `pairs`。

单次配对存在模型随机性。两组都通过不能证明方法有效；当前组仍有遗漏时，应保留失败证据。重复统计只报告观测次数及审阅结论，不自动宣布稳定提升。不要通过放宽判定、删掉失败轮次或把咨询次数作为质量得分来制造改善。

| --- | --- | --- | --- | --- |
| autonomous | baseline | 通过 | 非强制，实际咨询两位岗位 | 四项标准通过，保留一项非阻塞备注 |

具体反例均是对设计文字的推演，不是业务应用运行测试：

- 自主场景当前稿同时要求 `done ⇔ resolvedAt 非空`、合并子条目完成但只有主条目有完成时间、重开保留当前完成时间，合法操作无法满足全部规则；迁移前后的计数断言也未区分旧状态，仍会误拒合法数据。解除合并又缺少保存原状态的设计。
- 明确协作场景基线稿承诺恢复合并前 `status/startedAt/resolvedAt`，但只设计了重开用的处理历史字段，未给这些合并快照的数据落点，级联覆盖后无法恢复。
- 明确协作场景当前稿补齐了快照与历史路径，但启动时仅验证两个总数相等，不能满足 AC8 的逐条一致性要求。一条 `done/无完成时间` 与一条 `pending/有完成时间` 可使两项计数都为 1，从而错误放过不一致数据。

新增阻塞项会阻止质量通过，即使四项既定标准均已满足。离线汇总验证了全部引用与哈希，最终为三份通过、三份失败，退出码 `1` 表示已观察到质量失败，不是模型执行异常。源码与编译后 CLI 的离线汇总逐字节一致，帮助和汇总模式没有调用模型。一次自主配对的 `migration-reopen` 标准出现当前稿相对基线的退步；这里只记录本例结果，不据此断言新方法总体更差或更好。

所有正文、执行证据和审阅记录均保留，旧版演示及历史对照未改动。102 项离线测试、代码检查、构建、源码/编译入口启动与文档检查通过。真实模型本轮只跑每场景一次配对；重复轮次隔离、顺序交替和汇总分母由离线用例验证，尚无多次真实配对的稳定性结论。尚未扩大生产角色的自主运行或语义验收能力。

## 2026-11-16 首轮结果：咨询发生，质量尚未达标

两组均成功发布一个 V3，保留合成 V1/V2 的文件和索引，发布正文与 V3 文件一致，结束无残留占用。基线组没有咨询专业同事；当前组在首次发布前成功取得研发和测试两份回复。当前组随后重写正文并发布，工具记录未显示对最终重写稿再次读取核查；这不足以证明最终稿已完成复核。

逐项读取完整正文及内部回复后的判断：

| 项目 | 基线组 | 当前方法组 |
| --- | --- | --- |
| 事实依据 | 已纠正虚构试用与已验收的错误表述 | 同样纠正，并标注设计输入未经验证 |
| 合并状态 | 冻结子条目与批量改写状态仍冲突 | 增加了由主条目发起同步的说明，但完成、重开、再次处理的组合路径仍有矛盾 |
| 结构迁移 | 明确指出新增三列属于结构变更 | 删除了“无需结构变更”，新增快照字段与事件表，却没有明确结构升级规则；此项未比基线更清楚 |
| 迁移重复执行 | 保留每次启动的全库计数断言，会误判合法数据 | 研发指出反例，正文改为迁移时点一次校验，但 AC5 仍要求两次执行都进行全库断言，缺少一致的跳过/校验规则 |

当前方法提高了本例中可观察的发布前咨询行为，尚不能据此认定最终方案质量得到稳定提升。两组只是一次合成任务运行，没有业务实现或运行验收，也不证明长期自主能力。当前组的原始失败产物继续保留，不在验证后手工修成“通过”。

下一轮至少用以下路径复核最终成稿，而非只确认咨询次数：

1. 子条目合并前为 `pending`，主条目完成后子条目被同步为 `done`，再重开主条目并开始处理。当前稿要求子条目“不同步、保持不变”，AC2 却要求它与合并前快照一致；应明确最终字段值并同时修订规则和 AC。
2. 迁移结束后正常完成一个合并组，子条目 `status=done` 但其 `resolvedAt` 没有同步。再次运行迁移时，应明确是否依据版本标记跳过；不能又要求全库 `count(done)==count(resolvedAt 非空)` 必须成立。

这些是设计文字的反例推演，不是已实现应用的运行测试。后续改进应重新运行相同输入并审阅完整结果，不能仅添加更长提示或据此自动标记质量通过。

## 文件正文不一致的复跑与修复

用户随后复跑的证据目录为 `/var/folders/nq/4dbss1_n7n5g160x6_x9_gn40000gn/T/personal-agent-publication-review-nKEoJW`。两组执行、旧版保留和 V3 发布成功，但 `fileMatchesPublication` 均为 `false`。实际差异包含验收条目数量、章节引用和正文措辞修改，不能归为单纯空白差异；当前组的专业咨询检查仍为 `true`。

原因是旧发布接口让模型分别生成文件正文与工具 `content`，两份文本没有同一来源约束。现新增 `document.sourcePath`：宿主直接读取最终 UTF-8 文件，保存精确正文快照，并在成功收尾时校验路径和内容未变。文件发生变化时拒绝旧快照；同轮重新登记同标题文档可更新草稿，历史版本继续保留。纯文本 `content` 发布仍支持，但不绑定来源文件；两者不能同时传。

验证案例升级为 `publication-review-v2`，保留原有矛盾设计稿，只调整两组共有的文件发布要求。新增 `fileSourceUsed` 检查，正文比较改为完整字符串相等，不再忽略首尾空白。本次接口修复不应被算作语义复核方法本身的质量提升；旧证据与失败结果保持原样。
