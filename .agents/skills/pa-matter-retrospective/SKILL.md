# PA 事项与架构复盘

以用户关注的事项和预期为起点，解释发生了什么、为什么发生，以及哪些问题属于本次任务、哪些值得在 PA 系统层修复。把可核实的事实、推断、建议与未验证项分开；不要把单个工具或模型的表现直接等同于系统能力。

## 1. 确定范围并收集证据

- 识别事项 ID、用户目标、关键轮次和期望结果。链接指向本机工作台时，优先使用当前登录者有权访问的只读接口；按需核对事项消息、内部协作、运行通知、成果及关联会话。从当前路由实现核实可用接口，例如按需检查 `src/server/routes/matters.ts` 的事项详情；没有访问权限或证据缺失时说明缺口，不猜测。
- 对时间、组织、工作区、角色和执行模式进行关联。追溯历史策略时核对事件时间、运行版本或构建及相关 Git 历史；无法确定实际部署版本时标为未知。核对切换前后的范围，不能把事项当前绑定或后一次运行配置套到历史轮次。需要读取本地数据库或会话文件时采用只读方式；不得为了复盘触发真实任务、修改业务仓库或用户数据。
- 从用户输入、主责回复、内部委托、旁听、工具调用和结果、运行错误、交付物等证据重建关键时间线。记录有用的时间、消息或事件定位，以及与结论直接相关的简短证据；区分用户要求、角色陈述、工具返回和宿主实际行为。
- 工具启动清单只能证明当时报告可用，不能证明工具成功调用；调用完成不等于目标内容已被完整阅读或结论正确。日志缺失、截断、失败、异步任务及临时文件失效都应标明。对敏感数据只展示完成分析所需的最小内容，不把私有会话、路径或密钥写入可分享源码和文档。

## 2. 分析事项本身

- 比较用户预期、实际过程和结果，识别具体偏差与影响；沿触发条件、关键决策、工具调用与结果追溯因果。区分角色判断、信息不足、工具/供应商行为、调用失败、上下文接续和交互呈现等可能原因。
- 核实角色当时知道什么、可以做什么、实际做了什么。检查是否有其他可行路径、是否已有证据支持该路径，以及在当时的授权和运行环境下它是否可用；不要以现在的权限推断历史。
- 对无法证实的根因给出待验证的假设和最小验证方式，避免用提示词或单一工具改动替代根因定位。

## 3. 从 PA 架构重新审视

沿仓库的 [开发导航](../../../AGENTS.md) 找到相关模块 README 和实现，再按需追踪调用方、配置、数据流、UI、文档和测试。以当前源码及运行记录核实设计与现状，注意两者可能不一致。根据问题检查：

- **能力与边界**：Pi/runtime 实际装配、扩展与 MCP、角色定义、Skills、工具握手、会话和用户授权；区分可用能力、岗位职责、事项协作规则及操作系统权限。
- **协作与状态**：主责和事项名册、委托链、旁听/验收、跨轮上下文与会话、资料空间、结果归档、权限和组织隔离。确认问题属于单次执行还是多个路径共享的机制。
- **可观察性**：用户和角色能否知道实际能力、来源、执行结果、失败及限制；检查声明、界面、文档和事实是否一致。对证据缺失先指出观测缺口，不把缺失当作行为未发生。
- **方案归属与影响**：比较事项内处置、角色/方法指导、插件与工具、编排/runtime、存储/权限和 UI 等可能改动位置。说明最小有效修复、受益的其他场景、兼容性及可能改变的边界，避免只为某个工具、岗位或案例打补丁。

## 4. 给出结论并按授权推进

先回答用户最关心的问题，再列出：关键证据与原因；PA 已有能力、实际限制和证据缺口；按优先级排列的事项级及系统级建议；验证方法和尚未验证的风险。对每条建议说明目标、改动层及为何值得做；有多种方案时交代取舍。仅有复盘或询问思路的请求，给出分析和建议；用户同时要求优化或实现时，在授权范围内落实改动、更新相关文档，并按项目开发导航选择隔离环境和验证。不要把离线 fixture、启动成功或单次模型输出当成真实能力或长期效果的证明。
